# 洗车机 PLC 模拟器 · 接入标准

> 适用对象：给 `tools/plc-mock` 接一台新洗车机的人；改网页看板的人。
> 目标：**同一条命令、同一套看板、同一套测试脚本，换机型只换 `--plc <key>`**。
> 本文是契约。改接口必须同步改本文、`simulators/_template/`、`simulators/haitian/` 示例。

---

## 0. 一句话模型

一台洗车机 = **一份梯形图 CSV** + **一套现场物理反馈** + **一张工序表**。

```
启动流程  start.py --plc <key>
           │
           ├─ simulators.load(key)            读机型包（key/title/ladder_path/services…）
           ├─ simulator.build()               装载 CSV，写入上电常态输入 → 虚拟 PLC
           ├─ PlcRuntime(scan_ms, time_scale) 扫描循环：plant() → 强制值 → scan() → 记步
           ├─ SerialStub(PTY)                 冒充 FX 编程口，给盒子 main 用（可按需关）
           ├─ MqttBroker(1883)                本机 broker，给盒子 main / 看板用
           └─ Dashboard(18081)                网页看板，静态页 + JSON API
```

`core/` 与 `web/` **不含任何机型知识**：代码在 `simulators/<key>/`，资料（梯形图/原始件/说明）在 `docs/<机型>/`。

## 1. 分层与通用边界

| 层 | 路径 | 是否通用 | 说明 |
|---|---|---|---|
| 梯形图引擎 | `core/ladder.py` | 通用 | 解释执行 GX Works 导出的指令表（FX 指令集） |
| 扫描/追踪 | `core/runtime.py` | 通用 | 扫描循环、软元件目录、工序轨迹、强制值、前置检查动作 |
| 串口桩 | `core/serial_stub.py` + `core/framing.py` | 通用 | PTY 冒充 FX 编程口；帧协议与梯形图无关 |
| MQTT | `core/broker.py` | 通用 | 自建 broker（QoS0/1、通配符、看板下发） |
| 看板 | `core/dashboard.py` + `web/` | 通用 | 静态页按 bootstrap/state 渲染，不写死机型 |
| 机型接口 | `simulators/base.py` | 通用 | `SimulatorBase` 契约 |
| 机型实现 | `simulators/<key>/` | **每台一份** | 现场模型、工序表、命令点位、前置检查 |
| 机型资料 | `docs/<机型>/` | **每台一份** | 梯形图 CSV / `.gxw` / IO 表 / 原始件 / 机型说明 |
| 梯形图审查 | `devtools/` | 通用 | 直接吃 CSV，不依赖机型包 |

## 2. 机型包与资料目录：结构与注册

```
simulators/<key>/           ← 只放代码
├─ __init__.py        from .simulator import SIMULATOR      ← 必须
├─ simulator.py       机型类（继承 SimulatorBase）
├─ machine.py         现场条件表 / 命令点位 / 前置检查（可选，推荐）
└─ plant.py           物理模型（可选，可并入 simulator.py）

docs/<机型>/                ← 资料包：文档 + 图纸 + 数据
├─ README.md          机型说明（照 _模板/机型说明模板.md 写）
├─ <梯形图>.csv       运行时就读这份（ladder_path 指到这里）
├─ <工程>.gxw         原始工程，G5 闸门在 CSV 同目录自动找
└─ ...                 IO 表 / 厂商 .doc / 语义底稿
```

注册规则（`simulators/__init__.py`）：

- 包名即 `--plc` 的名字；
- `__init__.py` 必须暴露 `SIMULATOR`（类或实例）；
- **以 `_` 开头的包不注册**（`_template` 专用）；
- 某机型导入失败 → 打印 `[simulators] 跳过 xxx: 原因`，不影响其它机型（实测：故意抛异常时 `--list` 仍正常列出海天）。

## 3. 接口契约（`simulators/base.py`）

### 3.1 必选

| 成员 | 类型 | 说明 |
|---|---|---|
| `key` | str | 短名，`--plc` 用它 |
| `title` | str | 看板标题 |
| `ladder_path` | str | 梯形图 CSV 绝对路径（GX Works 导出，UTF-16 TSV，首列步号） |
| `build(preset=None)` | → Ladder | 装载梯形图，并写入**上电常态输入**（现场默认值）。不要在这里做机构动作 |
| `new_state()` | → dict | 物理模型内部状态（台车位置、刷子行程…），可为 `{}` |
| `plant(ladder, state)` | → None | 每扫描一次：读 `ladder.Y` → 推进物理状态 → 写回反馈 `ladder.X` |
| `flow()` | → list | 工序表，见 §4.1 |

### 3.2 可选（有默认值）

| 成员 | 默认 | 说明 |
|---|---|---|
| `transport` | `'fx-serial'` | 目前只有 `fx-serial`（PTY 冒充 FX 编程口）。Modbus 机型需先在 `core/` 实现通讯层 |
| `step_device` | `'D142'` | 表示“当前工序”的软元件；没有就设 `''` |
| `fault_device` | `'D2'` | 故障码软元件；没有就设 `''` |
| `services` | `{}` | 命令点位映射，见 §4.3 |
| `ready_signal` | `''` | 启动就绪的代表信号（海天 `M187`）。测试脚本用它判断“可以发启动了” |
| `preconditions` | `()` | 启动前置检查表，见 §4.2 |
| `key_devices` | `()` | 看板“关键点位”条固定展示的软元件（工序号/故障码自动置顶） |
| `fault_name(code)` | `''` | 故障码 → 说明 |
| `device_notes()` | `{}` | 软元件注解 `{名字: 说明}` |
| `apply_precondition(action, runtime)` | `False` | 执行前置检查按钮对应的“外部动作”（只改现场输入，不写命令位） |

### 3.3 执行顺序（不可改）

```
plant(ladder, state)   → 机构反馈写进 X
_apply_overrides()     → 人工强制值压过 plant（面板“强制写入”就靠这一步）
ladder.scan(dt)        → 梯形图读输入、算输出
_track_step()          → 记录工序跳变与停留
```

反过来的话：梯形图这一拍读到的是上一拍的反馈，短工序会丢；强制 X 点也会被 `plant()` 覆盖（这是修过的 bug）。

## 4. 数据结构

### 4.1 工序表 `flow()`

```python
{'value': 3, 'title': '前进洗车身', 'motion': 'forward',
 'sStep': 'S4', 'detail': '台车前进洗车身（S4）'}
```

| 字段 | 说明 |
|---|---|
| `value` | `step_device` 里实际出现的值，必须一一对应 |
| `title` | 看板节点名 |
| `motion` | `idle` / `forward` / `backward` / `end` —— 决定节点色与台车方向 |
| `sStep` | PLC 步号（展示用） |
| `detail` | 悬停/轨迹里的补充说明 |

### 4.2 启动前置检查 `preconditions`

机型侧定义（`machine.PRECONDITIONS`）：

```python
{'key': 'washPosition', 'title': '车辆停放到位', 'signal': 'M187',
 'action': 'carArrive', 'button': '车辆到位',
 'hint': '车开进装载位：M515=1、X3=0、X24=1；T61 确认 3 秒后 M187=1'}
```

| 字段 | 说明 |
|---|---|
| `key` | 与盒子点位表 `startChecks` 的 `signal` 名保持一致（`washPosition` / `startCondition` / …） |
| `signal` | PLC 软元件；**值 == 1 视为通过**（与盒子 `checkStart` 一致） |
| `action` | 看板按钮触发的动作名；空 = 该信号由梯形图合成，只展示不给按钮 |
| `button` | 按钮文案（外部动作，不是命令） |
| `hint` | 悬停说明 / 未通过时的提示 |

动作由机型实现 `apply_precondition(action, runtime)`（运行时只转发），**只改现场输入，绝不写命令位**（X45/M0/M100）。
`runtime` 提供 `lock`、`_write()`、`_parse_name()`、`clear_overrides()`、`plant_state` 给机型使用。

### 4.3 命令点位 `services`

```python
services = {
    'start': 'X45',      # startWashCar：只写这一个点
    'stop': 'M0',        # stopWashCar：只写这一个点
    'clearStop': 'M0',   # reset 第一步：写 0
    'reset': 'M100',     # reset 第二步：写 1（M100 由梯形图清）
}
```

必须与盒子 `src/common/config/default_point.cpp` 的 `table.services` 一致。
缺 `clearStop` 时复位退化为“只写 `reset`”，前端提示也会跟着变。

### 4.6 `POST /api/control`

| action | 参数 | 语义 |
|---|---|---|
| `demo-start` | — | 下发启动命令；盒子在线走 MQTT（`{"Manual start":1}`），否则直接写 `services.start` |
| `demo-stop` | — | 下发停止；同上（`{"stop":1}` / `services.stop`） |
| `demo-reset` | — | 下发复位；同上（`{"reset":1}` / `M0=0 → 1s → M100=1`） |
| `precondition` | `key` = 动作名（`carArrive` / `barLeft` / …） | 只改现场输入，不发命令 |
| `pause` / `resume` / `step` | — | 暂停 / 继续 / 单步 |
| `speed` | `timeScale` | 虚拟时钟倍速 |
| `override` | `device`, `value` | 强制写一个软元件（每扫描压一次，压过 plant） |
| `clear-overrides` | `device`（可选） | 解除强制（不带 device = 全清） |
| `clear-trail` | — | 清空工序轨迹 |

返回统一带 `{"ok": true, "action": …, "via": "mqtt" \| "plc", "status": {…§4.5…}}`；
`precondition` 额外返回 `preconditions`（供前端立即刷新）。

命令类动作在**机型没定义对应点位**（`services` 缺项）且没有盒子在线时返回
`{"ok": false, "error": "该机型没有定义这条命令的点位（services）"}`，前端要提示而不是假装成功。

### 4.7 `GET /api/mqtt` / `POST /api/mqtt/publish`

- `GET /api/mqtt?limit=200` → `{stats:{running,clients,subscriptions,received,sent,lastUpAt}, clients:[…], messages:[…]}`
- `POST /api/mqtt/publish` `{topic, payload, qos}` → `{ok, delivered, topic, qos}`

## 5. 网页看板开发约定

**硬规则：`web/` 里不许出现机型相关的软元件名。** 所有机型信息从 `bootstrap` / `state` 取：

| 界面元素 | 数据来源 |
|---|---|
| 标题 / 梯形图名 / 说明 | `sim.title` / `sim.ladder` / `sim.note` |
| “当前工序”卡与流程副标题 | `sim.stepDevice` |
| 流程节点与高亮 | `flow[]` + `step.value`；颜色按 `motion` |
| 关键点位条 | `keyPoints[]` + `values[]` |
| 前置检查面板 | `preconditions[]`：`passed` 决定红/绿点，`button`/`action` 决定按钮，空 action 显示“合成” |
| 命令按钮文案 | `services.start` / `stop` / `clearStop` / `reset` |
| “启动前要先复位”提示 | `sim.readySignal`（为空则退化为通用提示） |
| 预设里的“查询 D142” | 动态生成 `查询 ${sim.stepDevice}` |
| 软元件表 | `devices[]`（按 `refs` 降序，看板取前 120，其余靠搜索/筛选） |

**空状态必须优雅降级**（新机型可能没有这些概念）：

| 缺什么 | 看板行为 |
|---|---|
| `flow` 为空 / `stepDevice` 为空 | 流程图显示“该机型没有定义工序表”，KPI 只显示“当前工序” |
| `preconditions` 为空 | 整块“启动前置检查”隐藏（标题一起隐藏） |
| `services` 缺项 | 提示“该机型未定义命令点位”；无盒子时命令返回 `ok=false`，前端报错而不是假装下发 |
| `readySignal` 为空 | 发布区提示改为通用文案，不提具体信号 |

扩展看板时的顺序：

1. 后端加字段（`bootstrap` 或 `state`），**只加不改**；
2. `web/app.js` 里渲染（缺字段要有兜底）；
3. 更新本文 §4.4 / §4.5 与 `README.md` 的看板表。

## 6. 切换方式

| 场景 | 做法 |
|---|---|
| 列机型 | `python3 start.py --list` |
| 起指定机型 | `python3 start.py --plc <key>` |
| 机型自检 | `python3 start.py --plc <key> --check` |
| 全链路闭环 | `PLC=<key> bash tools/plc-mock/run_local_native.sh` |
| 闸门 | `PLC=<key> bash wsl-cross/verify.sh` |
| 看板 | 不用改——同一套静态页，按 bootstrap 渲染 |

**同一时间一个实例**：PTY 链接、broker 端口、看板端口都是独占的。
`start.py` 起组件前做端口预检，占用直接 `exit 4` 并列出占用者；`python3 start.py --stop` 收拾残留。

## 7. 接一台新机型（10 步）

1. **导 CSV**：GX Works 导出“指令表/助记符”，UTF-16 TSV，第一列是步号；放进 `docs/<机型>/`。
2. **建包**：`cp -r simulators/_template simulators/<key>`。
3. **建资料目录**：`mkdir -p docs/<机型>`，把 CSV / `.gxw` / IO 表放进去；
   再填元信息：`key` / `title` / `note` / `ladder_path`（用 `docs_path('机型目录', '文件.csv')`）。
4. **对齐上电常态输入**（`build()`）：哪些 X/M/D 是现场常态（如光电、车高、功能选择位），哪些“只能外部给”（如 `M515`）。
5. **写 `flow()`**：按洗车顺序列全，`value` 与 `step_device` 对齐；`motion` 标对方向。
6. **写 `plant()`**：把 `Y` 动作翻译成 `X` 反馈（台车位置、刷子行程、限位）。不写也能跑，但会卡在第一个“等反馈”。
7. **定 `services`**：与盒子点位表一致（start/stop/clearStop/reset）。
8. **定 `ready_signal` + `preconditions`**：与盒子 `startChecks` 对齐；能由外部输入决定的给 `action`。
9. **自检 + 跑一轮**：`--check` → `--plc <key>` → 看板点「复位」→ 等前置检查变绿 → 点「启动」。
10. **跑闸门**：`PLC=<key> bash wsl-cross/verify.sh --e2e`（需该机型能跑完整一轮）。

## 9. 已知边界与坑

- **transport 只有 `fx-serial`**：Modbus TCP 机型要先在 `core/` 写通讯层与桩，再谈接机型。
- **定时器基准**：`T0~T199 = 100ms`、`T200~T245 = 10ms`、`T246+ = 1ms`（与 FX3U 一致）。
- **CSV 是指令表不是梯形图**：`devtools/render.py` 可还原成梯形图核对；`gxw_check.py` 可与 `.gxw` 逐条对账。
- **资料位置**：梯形图与 `.gxw` 在 `docs/<机型>/`，G5 闸门靠“CSV 同目录”找 `.gxw`，别把两者分开放。
- **一个 PTY 只能给一个实例**：手动实例默认 `/tmp/vplc-pty`，脚本实例用 `/tmp/vplc-pty-<运行目录>`。
- **强制值只对“plant 写的 X”特殊**：强制在 `plant` 之后、`scan` 之前生效；对 M/D 是常规覆盖。
- **机型包导入异常会被静默跳过**（有打印）：`--list` 里少了一台先看启动日志。
- **`step_device` 上电可能没被写过**：`current_step()` 按 0 处理，不要返回 `None`。
- **看板文案禁止写死机型**：新增界面前先问“这个信息该从 bootstrap 哪个字段来”。

## 10. 变更规则

- 改 `SimulatorBase` 字段/方法 → 同步改 `_template`、`haitian` 示例、本文 §3/§4。
- 改 API 字段 → 只增不改；删字段要同时改 `web/app.js` 与本文。
- 改命令语义 → 以盒子代码为唯一依据（`HaiTianWashcar_service.cpp`），并在本文 §4.3 注明出处。
