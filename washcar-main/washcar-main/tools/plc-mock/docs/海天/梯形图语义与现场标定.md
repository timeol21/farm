## 语义口径以梯形图为准

CSV 只有指令表，没有图形。**所有助记符的语义口径，都是在 GX Works2 里打开
`金达路一号停车场洗车机.gxw` 的梯形图逐条对出来的**（2026-10-23）：

| 指令 | 操作数个数 | 含义 |
|------|-----------|------|
| `MOV/MOVP/DMOV/DMOVP` | 2 | 源在前、目标在后（`MOV K2 D142` = D142 ← 2） |
| `ADD/SUB/MUL/DIV/DADD/DSUB/DMUL/DDIV` 及 P 变体 | **3** | 源1 源2 **目标**（梯形图上是 `[MUL D3000 K60 D3004]`） |
| `INCP/DECP/DINCP` | **1** | 只有目标（自增/自减）—— 这三条不是三操作数 |
| `ZRST/ZRSTP` | 2 | 起止 |
| `BMOV` | 3 | 源、目标、点数 |
| `SUM` / `SPD` | 2 / 3 | 求和 / 测脉冲周期 |

**触点助记符的 I 后缀 = 反**（三菱 FX 惯例）：`LDI`/`ANI`/`ORI` 取反，`LDP`/`LDF`/`ANDP`/`ANDF`/`ORP`/`ORF` 是边沿。
这一条很要紧：程序里 `LD M520 / ORI M570` 读作「M520 **或** M570 取反」，
`M7`（机构未回原位）里那串 `ORI X012` 是 `!X012`，与 `M1`（启动前置条件）要求 X012~X017 全为 1 并不冲突。

`C` 区（计数器）是 **32 位（DC）**，占两个字（Cn 低字、Cn+1 高字），预设定和比较都按双字走
（程序里写的是 `LDD> C220 K20`、`ANDD< C220 D45`）。FX 的 C 计数器是「**计数输入 ON 的每个扫描周期 +1**」，
到预设定值停住、触点导通；计数输入断开时保持当前值，`RST` 清零。
所以程序里 `LDP X002 / ORF X002 / OUT C220 D534` 的意思是「X002 的**每个边沿**计一次」。

> **没有预设定值的计数器，触点不通。** 2026-10-23 修过一个真 bug：原来 C 区触点算的是
> `c_dword >= limit`，当 `limit=0`（程序里根本没有 `OUT Cn`，这个计数器不存在）时恒为真，
> 于是 `ANI C0` 这类条件永远为假 —— 海天工程 pc=1956 的 `ANI C0` 直接把前进输出 `Y030` 压死，
> 台车不动 → 洗车流程走不下去。现在没有预设定值就返回 0（触点不通）。

操作数的三种复合写法：

| 写法 | 含义 |
|------|------|
| `K750` | 常量 |
| `D499Z0` | 变址：D499 + 变址寄存器 Z0 的值 |
| `K4M260` | 点数前缀：4 点、起点 M260（M 区一点 = 16 位） |

`TO` / `FROM` 是特殊缓冲存储器传送（4 个操作数），不参与状态机，模拟器按
"已识别但不仿真"记账（`ladder.unsupported`）。

## FX3U 步进梯形图（STL）的执行语义

海天工程的主流程是 **STL 步进梯形图**，不是普通顺序梯形图。这套语义决定了模拟器的执行模型：

- **步末标记是 `OUT S0`**。步的范围 = `STL Sn` 到该步内**最后一条** `OUT S0`；
  **步末标记之后的指令是公共代码，每扫描周期无条件执行**。海天工程里公共代码有两段：
  主程序开头上电初始化段，以及最后一个步（S29）之后的 560 多步 —— 里面就有
  **行走脉冲计数 C220、顶刷脉冲计数 C222/C224、整段故障检测**。按「下一个 STL」划步会把这段吞掉。
- **同一时刻只有一个步 ON**：`SET Sn`（n≠0）置位新步时复位当前步与 S0；`OUT Sn` 是步转移
  （线圈语义：条件不成立时目标步复位）；步末标记 `OUT S0` 结束当前步。
- **S0 = 设备停止状态**（HMI 报警表第 10 条「设备在停止状态 ON S0」）。上电由 `SET S0` 置位，
  离开初始步时复位 —— 所以洗车过程中 S0 是 0（`M537` 洗车中标志要求 `!S0`）。
- **S 步状态是瞬时的**：S20 步执行完立刻 `OUT S37` 转走，末态读 S20 一定是 0。
  要判断「有没有进过某一步」，必须记录扫描过程中是否激活过，不能看末态。

主流程（D142 映射见 `AGENTS.md §3.4`）：
`S0 → S1(就绪,1) → S20 → S37 → S21 → S3(洗车头,2) → S4(前进洗车身,3) → S5(洗车尾,4)
→ S6(后退洗车身,5) → S10(前进喷淋水,6) → S9(后退喷蜡水,7) → S12(前进风干,8) → S13(后退风干,9) → S15(洗车结束,10)`。
每步末尾还有 `OUT S17`（公共转移步 → 故障分类 → 复位后回 S15）。

## 交叉对账：把 .gxw 里的梯形图整份解出来

`devtools/gxw_check.py` 从 GX Works2 工程文件（`.gxw`）里独立解出**整份梯形图**，和 CSV 指令表逐条比对：

```
gxw 程序块: 5433 个元素, 5899 条软元件引用
CSV 指令表: 5433 条指令
[1] 梯形图结构逐条对账(类别 + 操作数)  5433 条全部一致, 差异 0 处
[2] 各类别条数   LD661/661 AND493/493 ANI675/675 OR322/322 OUT639/639
                ANB218/218 ORB204/204 MPS174/174 MRD77/77 MPP174/174 …
[3] 软元件引用顺序   5825 条 100% 同序
```

解码要点（GX Works2 的 `.gxw` = OLE → `_hdb` → 流 `12` = 程序块）：

- 记录格式 `[位置字节][长度 L][载荷 L-2 字节]`；**元素 = [类型记录][操作数记录…]**
- 类型记录首字节 = 元素类别：`00`=LD `01`=LDI `02`=LDP `03`=LDF `06`=OR `07`=ORI
  `08`=ORP `09`=ORF `0c`=AND `0d`=ANI `0e`=ANDP `0f`=ANDF `14`=INV `18`=ORB
  `19`=ANB `1a`=MPS `1b`=MRD `1c`=MPP `20/21`=OUT `23`=SET `24`=RST，其余是应用指令
- 软元件区标签：`90`=M `9c`=X `9d`=Y `98`=S `a8`=D `e8/e9`=K `c2`=T `c5`=C
  `f1`=点数前缀 `f0/cc`=Z `d0`=P标签 `d1`=I标签 `ea`=H

**梯形图的串并联拓扑就编码在类别码里**（LD 起支路 / AND 串联 / OR 并联 / ANB·ORB 合并 /
MPS·MRD·MPP 多输出），所以不需要坐标就能还原结构。

> 版面坐标：`.gxw` 里**没有**存屏幕坐标——记录首字节只有 7 个取值（触点恒为 `03`、
> 线圈 `04`、操作数按槽位 `04/05/06`），是种类/槽位码。GX Works 显示的版面是按同一套
> 结构现画的，`devtools/render.py` 用同样的规则还原，可与 GX Works 画面逐条对照。

## 现场故障反推（analysis/sweep_params.py，2026-10-23）

用 2026-10-22 的现场日志当唯一判据，把「理想机」变成「能复现现场故障的机器」。

### ① 现场症状是什么

真机跑云端 start → 盒子写 X45=1 → PLC 进洗车头 → **卡住** → 故障收场：

| 现象 | 现场证据 |
|------|----------|
| start 被接受 | `PLC_WRITE_RESULT point=x45, val=1, result=ok` |
| 进洗车头 | `PLC_KEY_STATE point=D142 val=2` |
| 卡在 D142=2 | 之后 2 分 08 秒，D142 一直是 2，每 500ms 上报一次 |
| 卡住期间采集正常 | 0 条「连接失败」、0 条「read failed」 |
| 故障收场 | `FaultReport payload={... "fault":25 ...}`，D142 随后 0 → 10（S15 洗车结束） |

`fault=25` 查实是 `pc=412 MOV K25 D2`，上一句是 `pc=409 OUT T99 K400`
—— **T99 = 40 秒原地停留超时**（主程序 pc=406-412：`ANI Y030 / ANI Y031 / ANI C0 / OUT T99 K400`）。

**复现判据**（三条同时成立才算复现，脚本 `devtools/analysis/sweep_params.py` 自动判）：
进过 S3（D142=2）→ 没走出去（D142 不再变 3..9）→ 出现过 D2=25 并最终收在 S15。

### ② 卡死的确切机制（从梯形图反推，不是猜）

S3 步（洗车头）里有一条**互锁**，让台车走不出洗车头：

```
pc=1946  LDD=  C220 D30      ← 台车脉冲数 == 洗车头位置？
pc=1947  OR   M26 / OR M28 / OR M29
pc=1950  ANI  X024            ← 车还在检测位
pc=1951  SET  M16             ← M16 = "台车到洗车头位置了"
...
pc=1964  LDI  M16             ← M16 一置位,前进输出 M22 被掐断
pc=1967  ANI  T3
pc=1968  OUT  M22
pc=1979  ANI  M39
pc=1980  OUT  Y030            ← 前进输出断 ⇒ 台车停
```

台车停在 `C220 = D30` 之后，S3→S4 的出口(pc=2026-2036)有两条路：

```
pc=2027  LD   X006            ← 顶刷下到位
pc=2028  LDD> C222 K38
pc=2029  ANI  Y011
pc=2030  ORB
pc=2032  LD   X010 / AND X014 ← 两侧刷回原位
pc=2034  ORD>= C220 D32       ← 或:台车走够 D32 个脉冲
pc=2036  SET  S4
```

**`C220 >= D32` 这条路在真机上走不通**：`D32 = D30 + 70`（P6#1 `DADD D30 K70 D32`），
而台车已经被 M16 冻在 `C220 = D30`，永远差 70 个脉冲。
⇒ 出口只剩「顶刷下到位 X006」+「两侧刷回原位 X010 & X014」这一条。
这两条里任意一条不成立，台车就一直停在洗车头 → **T99 满 40 秒 → D2=25 → S17 → S15**，
D142 轨迹正好是现场那样：`1 → 2`（卡住）`→ 10`。

### ③ 扫描了哪些参数、结果如何

`devtools/analysis/sweep_params.py` 扫的是梯形图里**只读不写、只能上位机/HMI 或现场传感器给**的量。
一维全扫 88 个组合（40 秒跑完，4 并行）：

| 参数 | 扫的值 | 结果 |
|------|--------|------|
| **D32**（S3→S4 行程门槛） | 0 / 70 / 72 / 100 / 200 / 600 / 1170 | **70~1170 全部复现**；0 不复现 |
| **X024**（光电B 车身检测） | 0 / 1 | 1 复现（另一种死法：台车一路走到 C220=1500 顶到 C220 预设定后卡死，同样 D2=25） |
| D30（洗车头位置） | 2 / 30 / 100 / 500 / 1100 | 不单独复现，但**决定台车停在哪**（分别停在 C220=4 / 32 / 102 / 502 / 1102） |
| D276 / M230 / X001 | 见脚本 | **全部不复现** |
| D121 / D256 / D250 / D368 / D370 | 0~2000 | 不复现 |
| D512~D548 各档 | 0 / 100 / 500 | 不复现 |
| M512 / M514 / M528 / M551 / M552 / X003 / X075 / X004 | 0 / 1 | 不复现（X075=0、X010=0、X014=0 直接挡住启动；X003=1、X001=1 卡在启动链） |

二维扫描 `D32 × D30` 给出规律：**`D32` 必须大于台车停住的那个位置（约 `D30+2`）才复现**：

| D32 \ D30 | 2 | 30 | 100 | 500 |
|-----------|----|----|-----|-----|
| 0 | 不复现 | 不复现 | 不复现 | 不复现 |
| 72 | **复现** | **复现** | 不复现 | 不复现 |
| 100 | **复现** | **复现** | 不复现 | 不复现 |
| 200 | **复现** | **复现** | **复现** | 不复现 |

**⇒ 真机上 `D32 = D30 + 70` 恒成立，这个不等式自动满足 —— 所以现场那次不是"参数填错了"，是互锁本身走不通。**

### ④ 能复现症状的参数组合（现场模式）

```bash
cd tools/plc-mock
python3 wash_cycle.py --field          # 现场模式：复现现场症状，退出码 0
python3 wash_cycle.py                   # 理想机基线：9 个工序全通，退出码 0
```

`wash_cycle.PRESETS['stall-s3-t99']` 只覆盖两处：

| 覆盖 | 值 | 为什么 |
|------|-----|--------|
| `D[32]` | 72 | 真机上 P6#1 `DADD D30 K70 D32` = D30+70 = 72。**模拟器的 32 位算术是空操作**（见下），D32 恒为 0，S3 出口的 `C220 >= D32` 恒成立，所以模拟器「总能」走出洗车头，现场那种卡死复现不出来。这里按真机的值补上。 |
| `X[6]` | 0 | 顶刷下限位。pc=1078 `ANDD< C222 K40` 把顶刷下行限在 40 个脉冲，顶刷下不到位 ⇒ 出口的 `X006` 那条路不成立。 |

复现结果（`analysis/sweep_params.py --preset`）：

```
D142 轨迹: None → 1 → 2 → 10            ← 与现场日志一致(卡在 2,然后 10)
S 步轨迹: S0 → S1 → S20 → S37 → S21 → S3 → S17 → S15
进过 S3=True  出 S3=False  D2=[25]  收在 S15=True  停顿=862 扫描(43 秒)@C220=4
```

### ⑤ 给现场的确认清单

| # | 去核对什么 | 必须满足的关系 | 出处指令位置 |
|---|-----------|----------------|--------------|
| 1 | **顶刷下限位开关 X006** | 洗车头步里必须能变成 1（顶刷确实下到位）。不成立 ⇒ 出口条件缺一半 | `pc=2027 LD X006`；顶刷行程上限 `pc=1078 ANDD< C222 K40` |
| 2 | **左/右刷开位 X010 / X014** | 两侧刷必须回到开位（X010=X014=1）。不成立 ⇒ 出口条件缺另一半 | `pc=2032 LD X010 / AND X014` |
| 3 | **顶刷下行机构** | 顶刷要能走到 40 个脉冲以上（C222>38）且 Y011 复位 | `pc=2028 LDD> C222 K38`、`pc=2029 ANI Y011` |
| 4 | **D30 洗车头位置参数** | `D30` 必须让台车在 `C220=D30` 停住（M16）。现场要核对这个值是不是装机标定值 | `pc=1946 LDD= C220 D30` → `pc=1951 SET M16` |
| 5 | **D32 是不是 72** | `D32 = D30 + 70`，由程序算，不要人工改；改了就和 M16 的互锁对不上 | `P6#1 DADD D30 K70 D32` |
| 6 | **T99 屏蔽位 M573** | `M573=1` 会把「原地停留 40 秒」这条报警屏蔽掉（现场若已屏蔽，就看不到 D2=25） | `pc=411 ANI M573` |
| 7 | **X024 光电B 车身检测** | 若 X024 一直为 1，M16 永远不置位，台车会一路走到 C220=1500 顶死 —— 另一种 D2=25 | `pc=1950 ANI X024` |

**任务书里点名的 D276 / M230 那条 C0 路径，实测复现不出 D2=25**，原因是梯形图自相矛盾：
`pc=406-409` 的 T99 线圈条件里含 `ANI C0` —— **C0 一置位，T99 反而不计时**。
所以"C0 掐断前进输出"和"报 D2=25"这两件事在梯形图里不可能同时发生。
（另外 `D804 = D276 - D800/2` 要能算出来，还得先让 P7#27 的 M31 置位，M31 又依赖 X004
在 `D802>=6` 的那一刻为 1 —— IO 表里 X4 名称是空的，这条现场要单独问。）

### ⑥ 本次挖出来的模拟器缺陷（未修，留底）

| 位置 | 现象 | 影响 |
|------|------|------|
| `ladder.py` `arith()` | `op.startswith('ADD')` 对 `'DADD'/'DADDP'/'DSUB'/'DSUBP'/'DMUL'` 全是 False ⇒ **所有 32 位算术都是空操作** | `D32 = D30+70` 没算 ⇒ D32 恒 0 ⇒ S3 出口恒成立 ⇒ 理想机「总能」走出洗车头。**修它之后默认基线不再 PASS**（D34/D36/D66… 一串标定值跟着变），要连带重标物理模型 |
| `ladder.py` `set_area_word()` | `MOV K45 T7` 在预设定未知时(`state[1]==0`)不更新到位标志 ⇒ T7 触点永远不通 | T7 是 S3 出口条件之一(`pc=2026 LD T7`) |
| `ladder.py` `run_counter()` | `number <= 0` 把 **C0 当成非法计数器**，且预设定在线圈断开时也被改写 | C0 触点恒 0 ⇒ `pc=1956 ANI C0` 恒成立。**本次已修**（FX3U：C0~C199 都是合法 16 位计数器；预设定只在线圈 ON 时传送）。修了之后基线轨迹不变 |

## 现场视频标定（2026-10-14 原视频）

拿现场真机洗车的原视频（service 视角，252 秒，`2026-10-14 14:11:13`～`14:15:25`）当基准，
跟模拟器基线逐项对。视频是**唯一一份真机正常完成一轮洗车**的证据。

|------|------|

⇒ **真机一轮洗车 = 车停稳到洗完 ≈ 4 分 10 秒（250 秒）**。
⇒ **机器本身完全正常**：顶刷、侧刷、水、泡沫、风干全都动 ⇒ 2026-10-22 那次卡在 D142=2
不是程序缺陷，是当时的互锁条件/参数不成立。

### 跟模拟器对：时间尺度不用重新标定

模拟器基线全程 270.5 秒，视频 ≈250 秒，**差 8%**。脉冲尺度也已被互证：
`D534 = 1500`（C220 预设定）对应官方轨道 9600mm ⇒ **6.4mm/脉冲**，
台车 20 脉冲/秒 = 128mm/s（龙门洗车机的常见速度）。
⇒ 之前设想的「按 90 秒锚点重新缩放时间尺度」**不做**，那会把已经自洽的物理模型改坏。

相位对不齐，留底：模拟器 2 秒就开水泵 + 发泡剂，视频 50 秒后才见水雾；
模拟器的喷淋水阀（Y47）在 130 秒才开，视频里第一道水雾更早。原因未定
（可能是机位看的是龙门而不是台车，也可能是模拟器的准备阶段偏短）。

### 视频暴露的新缺口：顶刷电机 Y0 在模拟器里恒不转

模拟器里水泵 / 发泡剂阀 / 顶刷水伐 / 侧刷正转反转 / 龙门前后 / 喷淋水阀 都动作了，
**只有顶刷电机 Y0 全程为 0**，而视频里顶刷明明在转。

根因（已定位到指令位置）：

- Y0 的置位点都在**步体**里：`SET Y000`（S3 步 `pc=1821`、S35 步 `pc=2841`）、
  `OUT Y000`（S9 步 `pc=3207`、S12 步 `pc=3386`）。
- 但 `pc=3779 OUT Y000` 落在 **S15 步末标记（`pc=3763`）之后的公共代码**里 ⇒ 每扫描执行一次。
- 它的条件链在扁平 CSV 里没有 rung 边界，按顺序执行算出来是
  `LD M1 → MPS → ANI T57 → OUT T151 → MPP → AND T57 → OUT T57 K15 → ANI T57 → OUT Y000`，
  结果 R = `M1 & T57 & !T57` ≡ 0 ⇒ **每扫描把 Y0 抹成 0**，步体里置的 1 全被覆盖。

**没改**。改它要么需要 GX Works 的图形 rung 边界，要么会动到已验证的基线。
⇒ 现场一条便宜的办法：盒子已经在采 `M1`（启动前置条件位），
再加采 `Y0`（顶刷正转）/ `Y2`、`Y3`（顶刷速度 1/2），下一轮现场跑动就能直接看到
真机顶刷电机有没有被驱动。

### 扫描提速：装载时编译一次，不再每条指令重新解释（2026-10-25）

原实现每扫描约 2259 条指令（公共代码 + 当前 STL 步），每条都走 exec_one()：

ladder.py 新增快速路径：

- scan() 默认走 _scan_fast()；每个程序块第一次执行时，把每条指令编译成闭包
  （触点/比较/栈操作/OUT/SET/RST/MOV/STL/CALL 等），运行时只做"取值 + 栈操作"。
- 没覆盖的指令（算术、SUM/SPD/BMOV、FROM/TO 等）回落到 exec_one，语义只有一份口径。
- 实例上覆盖了 exec_one（verify_mock.py 的 G3/G4c 插桩）时整轮自动回退旧路径，
  插桩工具不用改。
- wash_cycle.Trace 改用 Ladder.on_step 钩子，不再覆盖 exec_one，
  所以洗车演练和 analysis/sweep_params.py 也吃快速路径。
- plc_stub_ladder.py --legacy 可强制回旧路径做 A/B。

- verify_mock.py 新增 **G6**：快速/逐条两套实例跑同一串 600 扫描
  （复位、启动、随机 X/M/D/Z/C 扰动），逐扫描比较软元件、T/C、边沿记忆、子程序深度，

**桩的扫描节拍也改了**：原来每轮 scan() 完再 sleep(scan_ms)，

> 受系统定时器粒度影响，1~2ms 档的墙钟数字不能直接当盒子结论。

### 加速档与采集周期的关系（2026-10-25 WSL 实测）

|---|---|---|---|---|
| 1 | 50 | 20ms / 50ms | ~430s | 1→…→10 ✓ |
| 25 | 2 | 20ms / 50ms | **17s** | 1→…→10 ✓（2/2） |
| 50 | 1 | 20ms / 50ms | **9s** | 1→…→10 ✓（3/3） |

⇒ **上限仍是采集/上报周期，不是 CPU。** 主程序原来每读一个点固定等待 10ms，
47 个采集点一轮 ≈ **470ms**；D142=2/4 在 50 倍下只有 **113/123ms**，
旧采集节奏会整轮跳过它们 —— 这是"提速后漏工序"的真正原因，不是梯形图算错。

⇒ 本地 native 修法（只影响 WSL 验证，不改生产默认）：
- 运行目录的 config 把 `plcSerial.baudRate` 调到 115200 —— 主程序那 10ms 的串口等待
  **按波特率缩放**（9600→115200 即 10ms→0.83ms），所以本地采集一轮从 470ms 降到约 39ms；
  产品代码里**没有 mock 专用开关**，现场波特率仍是 9600 ⇒ 串口等待逐位不变；
- 运行目录的 config 另把 washcarMonitorIntervalMs 调到 50、acquisitionIntervalMs 调到 20。
- 50 倍 WSL 实测 3/3 采全，25 倍 2/2 采全。

⇒ 现场真实串口仍是 9600、每帧约 10ms，**盒子上的高倍速闭环仍受这个 470ms 采集周期限制**；
验收或现场对时请用 1 倍；本地快速验证用 25/50 倍。
⇒ 脚本仍然**等云端收到 D142=10 就走**，不固定死等。

⇒ **但要注意：把本地采集拉密是"绕过"，不是"修好"**。真正的失真在**模拟器的工序时长**：
梯形图推出来的工序时长（洗车头 5.6 虚拟秒）比真机短得多 —— 真机的"洗车头"是顶刷下降到位，
机械运动要几秒，而模拟器只给 5.6 虚拟秒。加速档把墙钟一压，这道工序就短过主程序的采样间隔了。
⇒ **⇒ 要让模拟器的工序时长贴近真机，得按现场视频给每道工序单独标定**（脉冲当量 + 机构动作时间），
那才是根治；本地把采集拉到 20ms 只是让当前这个失真不暴露。

## 2026-10-23 语义修正（与 FX3U 手册对齐）

解释器原来有 9 处与 FX 语义不符的实现。**都是潜伏错误** —— 修完演练轨迹不变
（仍走完 9 个工序），说明它们此前不是卡点的原因；但只要走到故障分支或换程序就会给出错值。

| # | 位置 | 原实现 | 修正 |
|---|------|--------|------|
| 1 | `c_dword` / `set_c_dword` | 所有 C 按 32 位双字存 | **C0~C199 单字、C200~C255 双字**；相邻计数器不再互相污染，`RST Cn` 不再清零 Cn+1 |
| 2 | `arith` | `DDIV/DDIVP` 落到 `else` 直接返回（空操作） | 32 位除法：商在 D/D+1、余数在 D+2/D+3 |
| 3 | `arith` | `DIV` 按 IEEE754 浮点写 | 整数商/余数：商在 D、余数在 D+1 |
| 4 | `arith` | 16 位 `MUL` 只写低字 | 写 32 位积（D+1:D）；`DMUL` 写 64 位 |
| 5 | `read_block` / `write_block` | `K4M` 当成 4×16=64 位 | `K<n>` = n*4 位 = `ceil(n/4)` 个字 |
| 6 | `reset_range` | `ZRST` 不处理 C/T（静默无效） | 支持 C/T（C 按宽度清，T 复位状态） |
| 7 | `run_timer` / `set_area_word` | 当前值无限累加；`MOV Kx Tn` 被忽略 | 到预设定封顶；`MOV` 可写定时器当前值 |
| 8 | `special` | M8011/M8012 周期错位 | M8011 = 10ms、M8012 = 100ms（50% 占空） |
| 9 | `plc_stub_ladder.handle_read` | D 值 > 0xFF 时帧体变成 5~6 个字符 | 固定 4 位 hex（低字节在前） |

第 9 条是**协议层**：帧体一变长，主机侧 `readD` 固定取 4 个字符就会错位。
第 1 条也是**真实 bug**：原实现里 Cn 的高字就是 Cn+1，`RST C4` 会把 C5 一起清零。

对应闸门：`G4g` 改为整数商余 + MUL 高字 + DDIV；新增 `G4h` 相邻计数器互不串扰、
`G4i` `ZRST` 清 C/T、`G4j` `K4M` 块跨度、`G4k` 定时器封顶 + 可写。
**`G4g` 原先把「浮点 DIV」写成断言，是闸门把错误固化了 —— 一并改掉。**
