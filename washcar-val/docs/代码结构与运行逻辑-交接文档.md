## 1. 这个项目是什么

一句话：**洗车机主控程序。云端通过 MQTT 下发洗车命令 → 表现层入队 → 解析层翻译成业务消息 → 业务层做安全校验并调数据层写 PLC 软元件 → 回执入上行队列 → 发出；同时后台按配置周期轮询 PLC 刷进缓存、检测变化，再由上报调度线程按周期把变化/故障/日报推入上行队列发回云端。**

范围（刻意只保留这些）：

| 有 | 没有 |
|---|---|
| 洗车业务状态机（海天 / 驿公里两种机型） | 摄像头 / RTSP |
| PLC 通讯（海天=三菱 FX 串口；驿公里=Modbus TCP） | AI 推理（yolov8 / 车牌） |
| MQTT 通讯（libmosquitto）：command / read / reboot + 四路上行 | HTTP 服务 |
| 三条有界队列 + 定频泵（原始 / 业务 / 上行）+ 线程统一管理 | SQLite 落库、断网补发 outbox |
| 上行定时上报调度（变化 / 故障 / 每日物料） | 单元测试 |
| 日志（异步，文件 + 控制台） | |

设计取舍：**PLC 协议实现和洗车业务逻辑是从正式版原样搬过来的**（那部分在真机上验证过，重写风险极高）；
被重写的是 MQTT 层——原来是 900 多行手写报文拼装，现在换成 libmosquitto + 队列 + 解析层。

## 2. 与 washcar-main / washcar-val 的关系

三套代码是**完全独立**的项目，各自有独立的构建目录和产物目录，互不引用：

| | washcar-main | washcar-val | **washcar-test（本项目）** |
|---|---|---|---|
| 定位 | 正式版（历史基线，别改） | 测试版：main + 删冗余外设 + 摄像头封装 | 精简版：只留 PLC + MQTT |
| 摄像头 / AI | 有 | 有（封装成 `IFrameSink`） | **无** |
| MQTT | 自实现协议（900+ 行） | 自实现协议 | **libmosquitto** |
| 编译单元 | 68 | 68 | **29** |
| 源码规模 | — | — | 9100 行（include + src） |

改 washcar-test **不要**去动另外两个目录里的任何文件。

### 3.1 路径纪律：所有产出都在 `washcar-test/` 内

`washcar-test` 是唯一的根。三套脚本（`build-on-box.sh` / `wsl-cross/*.sh` /
`check-box-env.sh`）的目录全部由**脚本自身位置**推导，不依赖当前工作目录，也不写死机器路径：

| 产出 | 本机（Windows/WSL） | 盒子 | 推导方式 |
|---|---|---|---|
| CMake 中间产物 | `build-wsl/` | `build-box/` | `${PROJECT_ROOT}/build-wsl`、`$SRC/build-box` |

| 运行时数据 | `deployed/data/` | `deployed/data/` | 由 `ProgramPath` 拼绝对路径：日志固定 `data/log`，其余取 `box.storageRoot` |
| 源码根 | `washcar-test/` | `~/program/washcar-test/` | `find_repo_root` 从脚本位置向上找 `CMakeLists.txt` |

**只有两处意外，且都是外部的、只读的**：

| 路径 | 性质 | 能否避免 |
|---|---|---|
| `/opt/rk3568-sysroot` | 交叉编译工具链的 sysroot，仓库外 | 不能。属于"环境"，不是"产出" |
| `/tmp/vplc-pty` | 虚拟 PLC 的伪终端，仅 `wsl-cross/dev.sh` 本地调试用 | 生产不涉及 |

`deploy-wsl.sh` 的 `BOX_DEST_DIR` 默认值原本是 `/home/ztl/washcar-test/deployed`，

> **表现层为什么既是"MQTT"又是"解析"**：这两件事都是"和外界换消息"的机械动作，
> 中间只隔一层 json。把它们分到两个目录，反而要多定义一个跨目录的队列和一个跨层契约。
> 现在合成一层后：对外只有 `PresentationLayer` 一个入口，对内 `MqttClient → rawBuffer →
> DownlinkPump → CommandParser → bizBuffer` 是一条直线。
>
> **`BusinessCommand` 放在 `common/message.h` 而不是 `presentation/`**：它是解析层与业务层
> 之间的契约，和 `PlcPointValues`（data ↔ business）同一性质。放 common 后两层互不 include。

**关键边界（这四条决定了架构是否成立，改代码时别破）**：

| 契约 | 位置 | 作用 |
|---|---|---|
| `IDeviceService` | `include/data_layer/idevice_service.h` | 业务层能碰到的**唯一**数据接口。返回 `PlcPointValues`，**没有一个 PLC 类型出现在签名里** |
| `IReportSink` | `include/common/message.h` | 业务层往外发报文的唯一出口。业务只说 `ReportKind`，不知道 topic 怎么拼 |
| `IPlcInstance` | `include/data_layer/fx_plc/iplc_instance.h` | 统一 FX 串口和 Modbus TCP；`FxPlcInstanceSet` 只按接口持有 |
| `IWashCarService` | `include/business_layer/washcar/washcar_service.h` | 两种机型统一接口，`BusinessLayer` 与 `ReportScheduler` 只认它 |

**为什么业务层彻底看不见 `FxPlcStatus`**：`FxPlcStatus` 是五张 `Y/M/D/X/S` map 的容器，
它的形状由 FX 协议决定。若业务层直接吃它，将来换 Modbus 或加机型就要改业务代码。
现在跨层只传 `PlcPointValues`（一个 `unordered_map<std::string,int>` + 几个取值辅助），
业务层用 `getBit('M', 187, on)` 这种**软元件表达式**取点，与协议实现解耦。

## 5. 启动时序（`src/main.cpp`，113 行，只有 7 段）

`main.cpp` 里**不出现任何业务、协议、线程、文件、信号、配置解析的细节**——程序目录解析、
`ConfigManager::load`、sink 装配、`std::signal` 全部下沉到了 `Common`。它只负责"按什么顺序调谁"。

> 程序**不再 `chdir`**。工作目录是进程级全局副作用，改了之后所有相对路径的含义都跟着变；
> 现在由 `common/path/ProgramPath` 算出程序目录，配置和日志各自拼自己的绝对路径。
> 好处：从任何目录、任何方式（systemd / 绝对路径 / 软链接）拉起，行为都一样，且不会影响第三方库的相对路径。

| 段 | 行 | 做什么 | 失败行为 |
|---|---|---|---|
| ① 运行时 init | 38-40 | `Common::instance().init(argv[0])`：程序目录 → **读 config.json** → 日志装配 → 线程预算 → 系统监控装配 → 退出信号 | `return -1` |
| ② 运行时 start | 43-45 | `Common::instance().start()`：启动日志线程 + dump 生效配置 + 启动指标采样线程 | `return -1`（指标采样失败只告警） |
| ③ 三条队列 | 52-58 | `rawBuffer`（原始报文，容量 `queueCapacity.downCapacity`）、`bizBuffer`（业务消息，同容量）、`upBuffer`（`queueCapacity.upCapacity`） | — |
| ④ 三层 init | 80-93 | `dataLayer.init()` → `businessLayer.init(dataLayer.device(), upBuffer, bizBuffer)` → `presentationLayer.init(rawBuffer, bizBuffer, upBuffer)` | `fail()`：反向 stop 已起的层 + `app.stop()`，`return -1` |
| ⑤ 三层 start | 97-104 | `dataLayer.start()` → `businessLayer.start()`（起命令分派线程）→ `presentationLayer.start()`（连 MQTT + 起两个泵） | 同上 |
| ⑥ 等退出 | 110 | `app.waitForExit()`：200ms 轮询 `g_running` | — |
| ⑦ 退出 | 115-118 | **顺序有意义**：`presentationLayer.stop()` → `businessLayer.stop()` → `dataLayer.stop()` → `app.stop()` | — |

> 为什么 `businessLayer.start()` 排在 `presentationLayer.start()` **之前**：
> 分派线程要先就位，表现层一开始收包就能立刻被消费。
> 反了也不会丢（命令在队列里等着），但上电瞬间的命令会多等一个节拍。

### 5.1 `Common::init()` 的六个阶段（顺序是硬约束）

| 阶段 | 做什么 | 为什么必须在这个位置 |
|---|---|---|
| 1 | `ProgramPath::init(argv0)`：读 `/proc/self/exe` 算出程序目录（拿不到退回 `argv[0]` 的绝对路径父目录）。**只算路径，不 `chdir`** | 后面所有绝对路径都基于它。不改工作目录，是为了不给第三方库留下全局副作用 |
| 2 | `ConfigManager::load(<程序目录>/config.json)` | 日志的级别 / 保留天数 / 队列容量都来自配置，必须排在日志之前；文件不存在会自动写模板并提示改 `boxNo / plcSerial.port / mqtt.*`。这一步只解析文件，不写日志、不建目录 |
| 3 | `LogSystem::init()` 装配日志 | 日志目录固定 `<程序目录>/data/log`，由它自己创建。**返回之后全项目可直接 `LOG_*`** |
| 4 | `ThreadManager::setLimit(concurrency.maxThreads)` | 必须排在"起第一条线程"之前。线程预算来自配置，所以排在 2 之后 |
| 5 | `SystemMonitor::init()` 装配指标采样 | 它把指标写进日志目录（`LogSystem::dir()`），所以必须排在 3 之后。**失败只告警**，不拦启动 |
| 6 | 装 `SIGINT` / `SIGTERM` | 与前面无依赖，放最后 |

> **为什么配置排在日志前面**：日志级别、保留天数、队列容量本身就写在 `config.json` 里。
> 不先读配置，日志只能按写死的值装起来。配置解析这一步不产生日志（失败走 stderr），
> 所以它挡在日志前面不会丢任何日志行。**日志仍然是第一个"装配完即可用"的子系统。**

`Common::start()`：`LogSystem::start()` 起日志线程 → 打 `>>> 日志级别: x, 目录: y` → `cfg.dumpToLog()`
→ 打 `>>> 系统状态监控: 每 Nms 一次` → `SystemMonitor::start()`。

`Common::stop()` **顺序不能反**：先 `SystemMonitor::stop()`（停采样线程 + 停专用 logger），
再 `LogSystem::stop()`（join + 写完队列）。反过来的话，采样线程会在日志线程已经 join 之后
继续 push，那些行直接丢掉。

**为什么 `init` 和 `start` 要拆开**（用户明确要求"该放初始化的就放初始化，该放开始的就放开始"）：

- 读配置、建目录、开文件、装配 sink 属于**初始化**，一次性、会失败、失败要当场知道；
- 起后台线程属于**启动**，是"开始工作"的语义，和三层 `start()` 在同一抽象层级；
- 合起来会出现"配置读完了但日志线程起不来"的半截状态，`main` 也没法选择在哪一刻开始落盘。

`init` 里就先 `registerLogger`（而不是等 `start` 之后），好处是 `init` 之后立刻能用 `LOG_*`：
消息先攒在无界队列里，`start` 之后统一刷出去，一条都不会丢。

### 5.2 配置读取的实现一行没搬

`Common` 只决定"**什么时候**读"，解析、校验、默认值、写模板、dump 全部还在原处：

| 文件 | 职责 |
|---|---|
| `common/config/config_manager.cpp` | `load()`：不存在 → `writeTemplate()` 写模板；存在 → `parseJson()`；解析失败走 `applyDefaults()` + WARN 不致命；成功后 `resolveEnvVars()` 并按 `box.boxType` 选出 `MachinePointTable` |
| `common/config/config_serialization.h` | JSON ↔ 结构体的逐字段映射 |
| `common/config/default_config.cpp` | 每一段配置的默认值 |
| `common/config/default_point.cpp` | 海天 / 驿公里两套默认软元件表 |
| `common/config/point.h` | `"M26"` ↔ `{'M', 26}` |

`Common::loadConfig()` 只包了三个动作：`exists()` 判模板是否刚生成 → `ConfigManager::load()` → 新模板时打一行提示。
真正的读取逻辑没有任何改动。

### 5.3 ④⑤ 两段为什么有 `fail()`

三层里任何一步失败，如果直接 `return -1`，已经起来的线程不会 `join`、日志队列里最后几条（往往正是失败原因）会丢。
所以 `main` 用三个 `bool` 记录"起没起来"，配一个 `fail()` lambda 反向收尾：

```cpp
auto fail = [&](const char* what) {
    std::cerr << ">>> 错误: " << what << std::endl;
    if (commStarted)     commLayer.stop();
    if (businessStarted) businessLayer.stop();
    if (dataStarted)     dataLayer.stop();
    common.stop();                 // 最后停日志，让上面每一步的收尾日志都落盘
    return -1;
};
```

实测（broker 不可达）：`exit=255`，日志里能看到
`[Report] scheduler stopped` → `[DeviceService] acquisition stopped`，收尾完整。

> 退出顺序：先断上游（不再产生报文、不再消费队列），再停业务（不再产生上报），最后停采集（不再写缓存），
> 日志压轴。反过来停会在关闭瞬间产生"队列里有报文但没人发"的脏状态。

**注意 `dataLayer.device()` 返回的是 `IDeviceService&`**——`main` 拿不到 `DeviceService`、
拿不到 `DeviceService`，也就没法绕过契约乱调。这是刻意的。

## 6. 线程模型

| 线程 | 谁创建 | 周期 | 干什么 | 注意 |
|---|---|---|---|---|
| 主线程 | `main()` | 200ms 轮询 | 装配 + `Common::waitForExit()` 等退出信号 | 不做业务 |
| 采集线程 | `DataLayer::start()` → `DeviceService::start()` | **`machine().acquisition.intervalMs`**，默认 500ms，下限 100ms | `gateway_.poll()` → 读全表 → **逐点比对，只写变化的点** → 标记 changed。**PLC 的唯一读者** | `start()` 先同步采一轮再起线程；循环用 `sleep_until` 到下一个周期点，采集耗时从周期里扣，不漂移 |
| MQTT 网络线程 | `mosquitto_loop_start()` | 库自己管 | 收发报文、心跳、重连 | 回调**只做一件事**：`RawMessage` 入队后立刻返回（毫秒级），不再执行业务 |
| 下行泵 | `PresentationLayer::start()` → `DownlinkPump::start()` | 50ms 一拍（`popWait` 超时值） | 出队 → `CommandParser::parse` → **push 进 bizBuffer** | **只解析不执行**，所以解析再慢也压不住 MQTT |
| 命令分派线程 | `BusinessLayer::start()` → `dispatchLoop()` | 50ms 一拍 | bizBuffer 出队 → `BusinessLayer::onCommand` → 洗车服务 | **命令在这里同步执行**（驿公里启动最长 3.2s）。执行期间后续命令在队列里排队，不堵上游 |
| 上行泵 | `PresentationLayer::start()` → `UplinkPump::start()` | 50ms 一拍 | 出队 → `mqtt.publish(endpointFor(kind), payload)` | 断链时**不消费队列**，睡 200ms 后再看 |
| 上报调度线程 | `BusinessLayer::start()` → `ReportScheduler::start()` | 100ms 节拍；变化/故障按 `timing.*IntervalMs` | 调 `executeValueChangeTask` / `executeFaultReportTask` / `executeDailyReportTask` | 只把报文推进队列，不管发没发出去 |
| 洗车监控线程 | `startWashCarStatusMonitor()`（命令成功后起） | `timing.washcarMonitorIntervalMs`（500ms） | 轮询 D142 进度 → 推 `monitor` | 洗车结束/故障时**自己退出并置 `statusMonitorRunning=false`**（不能调 `stopWashCarStatusMonitor()`，会自己 join 自己死锁） |
| 日志线程 | `LogSystem::start()` → `AsyncLogger::start()` | 队列驱动 | 落盘 `log_*.txt` | 由 `Common::start()` 在三层之前启动 |
| 指标采样线程 | `Common::start()` → `SystemMonitor::start()` | **`sysmon.intervalMs`**，默认 5000ms，下限 1000ms | 读 `/proc` `/sys` → 一行指标 → 专用 logger → `sys_*.txt` | 分片睡眠 200ms，`stop()` 最多等 200ms；只读内核文件，不碰 PLC / MQTT |

**线程总数**：稳态 **8 条**（日志 / 指标采样 / 采集 / 下行泵 / 分派 / 上行泵 / 上报调度 / MQTT 网络的库线程），
洗车过程中 +1（洗车监控）。全部由 `common/thread/ThreadManager` 统一发放，上限 `concurrency.maxThreads`（默认 16）。

### 6.1 所有线程都从 `ThreadManager` 取（不再各层自己 `new std::thread`）

**规则：任何要起线程的地方，写 `ManagedThread::start(name, fn)`，不要写 `std::thread`。**

```cpp
ManagedThread t;
if (!t.start("acquisition", [this]{ loop(); })) {   // false = 超上限或已在跑
    LOG_ERROR("[DeviceService] 线程预算不足，采集未启动");
    return;                                          // 调用方自己降级
}
```

| 能力 | 说明 |
|---|---|
| **全局上限** | 超过 `concurrency.maxThreads` 直接拒绝并打 ERROR（附当前存活线程列表），不再创建 |
| **登记表** | `snapshot()` 随时列出"现在活着哪些线程"，日志里能直接看到；退出时打印"剩余 0 条"即证明没有泄漏 |
| **异常兜底** | 线程体统一包了 `try/catch`，任一循环抛异常只结束该线程并记 ERROR，**不会 `std::terminate()` 把进程带走** |
| **命名** | `log` / `sysmon` / `acquisition` / `downlink` / `biz-dispatch` / `uplink` / `report` / `washcar-monitor` |
| **自动销号** | 线程函数一返回就从登记表移除（RAII guard），`count()` 始终是真实存活数，不等 `join` |

**为什么不做"固定 N 个 worker 的线程池"**：
本项目的线程都是**长驻阻塞循环**（采集、泵、调度），一个 worker 被一个循环占住就再也腾不出来。
池子比循环少 → 直接死锁；池子等于循环数 → 退化成一对一，只是多一层任务队列的壳。
真正要防的是"线程无节制增长"，所以做的是**有上限的登记 + 拒绝**，语义更贴合，出错时行为也更可预测。

**唯一不受管的线程**：`mosquitto_loop_start()` 起的网络线程。它是库内部的，
我们只能通过 `mosquitto_loop_stop()` 让它退出，管不到它的创建。所以预算里给它留了一个位置。

**线程安全要点**：

- `MessageBuffer` / `UplinkBuffer` 内部 `mutex_ + condition_variable`，可跨线程 push/pop。
  `popWait(out, timeoutMs)` 就是"定时器"：有数据立刻醒，没数据最多等一个 tick。
- `DeviceService` 有 `mutex_`（保护 PLC 集合与缓存）+ `keyStateMutex_`（保护关键点位日志基准）。
  **两把锁是必须的**：`logKeyStateChanges()` 在 `poll()` 的持锁段里被调用，
  `std::mutex` 不可重入，共用一把会自锁。
- `FxPlcInstance` 内每个方法都 `lock_guard(mutex_)`，串口帧不会交错。
- `MqttClient::publish` 有 `publishMutex_` + `connected_` 原子判断（`mosquitto_publish` 非线程安全）。
- `WashCarServiceBase::m_currentStatus` 是**共享成员**，多线程同时发命令会互相覆盖——
  现在只有下行泵一个线程调业务，暂时安全；`readPoints` 也在同一线程，安全。

## 7. 四条主链路

### 7.1 下行命令（云端 → PLC）

```
云端 publish flexem.{boxNo}.command        （分隔符由 mqtt.topicSeparator 决定，默认点号）
   │  payload 平铺 JSON，如 {"Manual start":1,"boxNo":"123456","time":1774500653}
   ▼
MqttClient::handleMessage                   ← topic→endpoint 查表归一化，未订阅的 topic 直接丢弃
   ▼
rawBuffer.push(RawMessage{endpoint,payload,recvMs})    ← ★ MQTT 线程到此结束，立刻返回（毫秒级）
   ┄┄┄┄┄┄┄┄┄┄ 第 1 段队列（削峰）┄┄┄┄┄┄┄┄┄┄
   ▼
DownlinkPump::loop（50ms 一拍，"downlink" 线程）
   │  popWait(raw, 50ms) 拿到报文
   ▼
CommandParser::parse(raw, err)              ← ★ 解析层：只翻译，不执行
   │  endpoint == "command" → classifyCommand() 按 JSON **字段名**判 CommandType
   │  endpoint == "read"    → extractRequestedPoints() 收集点位名
   │  endpoint == "reboot"  → CommandType::REBOOT
   │  认不出来 → UNKNOWN（就地丢 + 一条 WARN，**不往业务队列塞垃圾**）
   ▼
bizBuffer.push(BusinessCommand)             ← ★ 解析结果入业务队列，下行泵到此结束
   ┄┄┄┄┄┄┄┄┄┄ 第 2 段队列（解耦）┄┄┄┄┄┄┄┄┄┄
   ▼
BusinessLayer::dispatchLoop（50ms 一拍，"biz-dispatch" 线程）
   │  bizQueue_->popWait(cmd, 50ms)
   ▼
BusinessLayer::onCommand(cmd)               ← ★ 业务层入口（命令在这里**同步执行**）
   │  try/catch 兜住一切异常（这里抛出去会打死分派线程，后面所有命令都收不到）
   ├ READ → handleRead(cmd)
   │    └ service_->readPoints(points) → 组平铺 JSON + boxNo + time → push(READDATA)
   └ 其它 → dispatch(cmd)
        │  makeOperation() 统一补 reqSource="mqtt" / boxNo / plcId（缺 plcId 时按机型兜底）
        ├ START   → startWashCar(op) → 成功后 startWashCarStatusMonitor(op) → replySuccess()
        ├ STOP    → stopWashCar(op)
        ├ RESET   → resetWashCar(op)
        ├ ABORT   → abortWashCar(op)          （驿公里 machine abort）
        ├ STOP_WORK / STOP_SERVICE / RESET_SAFE
        ├ POINT_ON / POINT_OFF / POINT_STATUS / CLEAR_ALARM / CHANGE_MODE
        ├ REBOOT  → 默认只记 WARN；`mqtt.rebootEnabled=true` 时 raise(SIGTERM) 优雅退出
        └ 失败 → 只记 WARN 日志，**不回执**（协议约定）
   ▼
XxxWashCarService::startWashCar   (HaiTian...cpp / YiGongLi...cpp)
   │  ① checkStateMachine(START)      → 状态机前置校验（log_only 只记日志）
   │  ② 维护模式拦截（reqSource=="mqtt" && m_isMaintaining）
   │  ③ 取 PLC 当前状态快照（viewAllDeviceStatus）
   │  ④ checkStart(具体规则见 §10)
   │  ⑤ 按点位表拿写点位 → deviceService.forceFxM / forceFxX
   │     海天：写 X45=1
   │     驿公里：先写 M204=1 → sleep 200ms → 按 mode 写 M521/M522/M523 → 轮询确认 S20 ON
   ▼
BusinessLayer::replySuccess → upBuffer.push(Report{COMMAND_REPLY, {"message":"success","time":<int>}})
```

**注意**：`commandreply` 只在**成功**时发；失败只写日志、不回执。这是协议约定的行为，
代价是云端看不到失败原因（只能看盒子日志 `[Business] command failed: <type>, msg=<reason>`）。

`read` 分支不回复执，而是用 `readdata` 作为应答：

```
云端 publish flexem.{boxNo}.read   {"D142":null,"M1":null,"boxNo":"123456","time":null}
   ▼
CommandParser::extractRequestedPoints()   只挑 D/Y/M/X/S + 数字的键（boxNo/time 自动过滤）
   ▼
IWashCarService::readPoints(points)       实现在 WashCarServiceBase（两机型共用）
   │  走 viewAllDeviceStatus() 读缓存；D 回整数，M/Y/X/S 回 0/1；采不到的点不进报文
   ▼
upBuffer.push(Report{READDATA, ...})      {"D142":3,"M1":0,"boxNo":"123456","time":1782121980}
```

### 7.2 上行状态（PLC → 云端）

```
业务层任意位置 → sendReport(kind, payload) / sink->push(Report{...})
   ▼
upBuffer.push(Report)
   │  monitor / readdata 是"当前状态" → 顶掉队列里同类旧报文（replaced++）
   │  pushalarm / commandreply 是"事件" → 逐条排队，满才丢最旧（dropped++）
   ┄┄┄┄┄┄┄┄┄┄ 队列边界 ┄┄┄┄┄┄┄┄┄┄
   ▼
UplinkPump::loop（50ms 一拍）
   │  !mqtt_.isConnected() → 睡 200ms 再来，**不消费队列**（报文留在队列里等重连）
   │  已连接 → popWait(report, 50ms)
   ▼
mqtt_.publish(comm::endpointFor(report.kind), report.payload)
   ▼
topic = flexem{sep}{boxNo}{sep}{endpoint}
```

| endpoint | 谁发 | 何时发 | payload |
|---|---|---|---|
| `monitor` | `HaiTian/YiGongLi::startWashCarStatusMonitor` 的线程 | 洗车中每 500ms | 海天 `{"D142":<步骤>,"boxNo":...,"time":...}`；驿公里带 `sState/stepName` |
| `monitor` | `executeValueChangeTask` | 由 `ReportScheduler` 按 `timing.valueChangeIntervalMs`（默认 3s）驱动 | 属性类点位平铺 + `boxNo`/`time` |
| `commandreply` | `BusinessLayer::replySuccess` | 命令成功 | `{"message":"success","time":<整型>}` |
| `readdata` | `BusinessLayer::handleRead` | 收到 `read` 后 | 请求的点位值 + `boxNo`/`time` |
| `pushalarm` | `executeFaultReportTask` | 由 `ReportScheduler` 按 `timing.faultReportIntervalMs`（默认 3s）驱动 | 故障点位 + `faultName` + `boxNo`/`time` |
| `pushalarm` | `executeDailyReportTask` | 每天 `dailyReportHour:Minute` 一次 | 物料点（异常才发） |

topic 统一由 `MqttClient::publish(endpoint, payload)` 拼成 `flexem{sep}{boxNo}{sep}{endpoint}`，
全项目只有这一处拼 topic。

### 7.3 PLC 采集（后台）

```
DeviceService::loop (device_service.cpp:95)   每 intervalMs（默认 500ms）
   ▼
DeviceService::poll() (device_service.cpp)
   │  ① 持锁收集目标（plcId + IPlcInstance*）后立刻放锁
   │  ② 逐台 IO（不持锁，串口等待不拖住业务读缓存）：
   │     ├ PLC 未连接 → 尝试 connect()，失败跳过本轮
   │     ├ D 点：**逐个** readD（每个 D 独立地址，不能合）
   │     ├ Y 点：**按组** readY(group)，一次回 1 字节 = 8 个位
   │     ├ X 点：**按组** readX(group)，同上
   │     ├ M 点：**逐个** readM（一次只回一位）
   │     ├ S 点：**逐个** readS
   │     └ logReadFailure()：失败第 1 次和每第 60 次各打一条（防拔线刷屏）
   │  ③ 重新持锁合并结果：**逐点比对，只有值变了才写缓存**（见 §7.5.1）
   │     首轮无条件写全表并置 changed=true（保证业务侧开局拿得到一次全量）
   │  ④ logKeyStateChanges()：仅在本轮确有变化时调用，keyStatePoints 里的点值变了打一条日志
   │     （用 keyStateMutex_，避免与 mutex_ 自锁）
   ▼
（被业务层读走）viewAllDeviceStatus() / getChanged()
```

### 7.5 单向数据流：PLC 只有采集线程一个读者

这是整个数据层最重要的一条纪律，改代码时别破：

```
PLC ──(采集线程，每 intervalMs 一轮)──► DeviceService::cache_ ──► 业务层（只读快照）
```

- 采集线程是**唯一**会发起 PLC 读写请求的线程（写点位 `forceFxM/forceFxX` 除外，那是命令通路）。
- 业务层所有"读"，包括状态判定、`read` 命令的 `readdata`、监控线程取进度，
  都只是对 `cache_` 做一次 map 拷贝，**不会产生任何串口 / TCP 请求**。
- 因此业务层拿到的是"最多滞后一个采集周期"的快照——这是设计代价，不是 bug。
  要更实时就调小 `machine.<type>.acquisition.intervalMs`。

**为什么不能让业务层现场读**（早先的实现犯过这个错，已修）：

| 后果 | 原因 |
|---|---|
| 命令响应被拖慢 | 串口只有一条，业务线程和采集线程抢同一把锁，要等一整轮采集（几百 ms ~ 数秒） |
| 断线时日志爆炸 | 缓存永远空 → `hasSnapshot()` 恒 false → **每条命令都去开一次串口** |
| 状态误判 | 现场读到的是"此刻"，而业务判定逻辑是按快照序列设计的，两者混用会前后不一致 |

**启动时序的兜底**：`DeviceService::start()` 在起采集线程**之前**先同步采一轮。
所以 `start()` 返回时缓存里一定已有数据（或明确失败并打 WARN），
上电后第一个命令不会拿到空表。这是全系统唯一一处发生在采集线程之外的 PLC 读，位置固定、时机可控。

**验证结论**（mock PLC 计数，见 §13 技术债 13.10）：
缓存就绪后连续 100 次 `viewAllDeviceStatus()`，PLC 读调用次数 **零增长**；
断线场景连续 50 次读全部返回空表，同样零增长。

### 7.5.1 缓存写入策略：值不变就不写

采集是**周期性读**（`machine.<type>.acquisition.intervalMs`，默认 500ms，下限 100ms），
但写缓存是**按变化写**。`DeviceService::mergeIntoCache()` 对每个点做三选一：

| 情况 | 动作 |
|---|---|
| 与缓存里相同 | **跳过，不写** |
| 与缓存里不同 | 只写这一个点 |
| 本轮没读到（读失败） | **保留旧值**，不删除 |

这一条带来四个可观察的差异（相对"整表覆盖"的老实现）：

1. **写入次数与读次数解耦**。稳态（洗车机待机）时每分钟读 60 轮 × 29 点 = 1740 次读，
   写入次数为 0。`DeviceService::stats()` 的 `freshPoints` 与 `writtenPoints` 之差就是这个比例，
   `DeviceService::stop()` 会把它打进日志：
   `[DeviceService] acquisition stopped, polls=9, freshPoints=26, writtenPoints=6, unchanged=76%`
2. **单点读失败不会丢点**。老实现整表覆盖，一次串口丢包就让这个点从缓存里消失，
   业务层 `has()` 判 false 后会把它当成"没采到"进而 `WASHCAR_NO_PLC`。
3. **`changed` 标志语义变精确**。它就是"本轮确实有值变了"，
   不会因为一次全等覆盖被无条件触发，`monitor` 上报节奏因此只跟真实变化相关。
4. **`keyStateChanges` 日志只在真变化时做比对**，稳态零开销。

> 注意：缓存里存的是"最后一次变化时的值"，**不记录读取时间**。
> 需要判断数据新鲜度请看 `stats().polls` 是否在增长，不要用点的值推断。

**验证结论**（mock PLC，23 项断言全通过）：

| 场景 | 结果 |
|---|---|
| 连续 5 轮值不变 | 读 15 次，写入 **0** 次，`changed` 保持 false |
| 只改 1 个点 | 写入 **1** 个点，不是整表覆盖 |
| 同时改 2 个点 | 写入 2 个点 |
| 某点读失败 | 写入 0 次，旧值保留，`changed` 不置位 |
| 业务读快照 100 次 | PLC 读调用 **0** 次 |

**组读规则（省往返的关键）**：X/Y 的组号 = `addr / 10`，组内位号 = `addr % 10`，
**只有 bit 0~7 有效**（一次回 1 字节）。所以：

- X30~X37 是同一组（group 3），8 个点一次读完；
- X38 / X39 读不出来（bit 8/9 超出字节）——点位表里别写这种地址。

对于海天 30 个 X 点，按组读只要 8 次往返，不是 30 次。

### 7.4 队列溢出与断链行为（这决定了"会不会丢报文"）

| 场景 | rawBuffer（原始报文） | bizBuffer（业务消息） | upBuffer（上行报文） |
|---|---|---|---|---|
| 正常 | 按序消费 | 按序消费 | 按序发出 |
| 短时堆积 | 满了丢**队首**（最旧），`dropped_++` | 满了丢**队首**（最旧），`dropped_++` | 满了丢**队首**（最旧），`dropped_++` |
| broker 断链 | 不受影响（MQTT 收不到就没有报文） | 不受影响（没人往里投） | **上行泵不消费**，队列自己收敛：`monitor/readdata` 只留最新一条，`pushalarm/commandreply` 最多攒 128 条；重连后把最新的这批发出去 |
| 命令执行很慢 | 可能堆积（下行泵很快，一般不堆） | **在这里堆**——驿公里一条启动占 3.2s，后续命令排队 | 不受影响 |
| 关机 | `DownlinkPump::stop()` 调 `shutdown()`，唤醒等待者、拒绝新 push | `BusinessLayer::stop()` 调 `shutdown()`，唤醒分派线程 | 同 `UplinkBuffer::shutdown()` |

> **`dropped(biz)` 是最该盯的计数**：它不为 0 说明命令在业务侧积压到溢出，
> 通常是"洗车机正在执行一条长命令，云端又连发了好几条"。清理办法是看 `[Business]` 日志的时间线，
> 而不是去加队列容量——容量只是把问题往后推。

> 这是本项目**唯一的"补发"机制**：断链期间 `monitor` 只保留最新快照，
> 重连后立刻补一条当前状态（而不是把断链期间每 3s 的历史全发一遍）。
> 历史过程无法还原，这是有意的取舍——洗车机关心"现在是什么状态"。

### 7.6 系统状态监控（sysmon）：盒子自己活得好不好

前四条链路解决"洗车机在干什么"，这一条解决"盒子还活着吗"。现场最难查的故障
——白天正常、晚上卡死、跑三天内存涨满、日志把 Flash 写满——都在这条链路的覆盖范围内。

**输出是专用文件 `data/log/sys_YYYY-MM-DD.txt`**，与业务日志 `log_*.txt` 完全分开：

```
[2026-11-01 16:17:56] cpu=8.5% load1=0.9 load5=0.5 load15=0.2 mem_used=693MB mem_total=15877MB mem_pct=4.4% mem_avail=15184MB swap_used=0MB swap_total=4096MB temp=na freq=na rss=7.1MB threads=4 disk_free=974922.2GB disk_total=1031018.4GB disk_used_pct=5.4% uptime=97s
```

| 字段 | 来源 | 现场怎么用 |
|---|---|---|
| `cpu` | `/proc/stat` 两次采样差分 | 持续 > 80% 说明有死循环或线程自旋 |
| `load1/5/15` | `/proc/loadavg` | 单核机器上 load1 长期 > 1 就是过载 |
| `mem_used/total/pct/avail` | `/proc/meminfo`（用 `MemAvailable` 算已用） | `mem_used` **单调上涨不回落** = 内存泄漏 |
| `swap_used/total` | 同上 | 一旦大量使用 swap，响应会明显变慢 |
| `temp` | `/sys/class/thermal/thermal_zoneN/temp` | RK3568 过 80℃ 会降频，表现为"越跑越卡" |
| `freq` | `cpufreq/scaling_cur_freq` | 配合 temp 看是否被温控限频 |
| `rss` / `threads` | `/proc/self/status` | `threads` 持续上涨 = 线程在泄漏（本项目线程数应恒定） |
| `disk_free/total/used_pct` | `statvfs(logDir)` | Flash 写满后日志和配置全部失效，这是"跑几天就挂"的头号原因 |
| `uptime` | `/proc/uptime` | 和日志里的启动时间对不上 = 进程被重启过 |

**为什么单独一个 logger 而不是复用 `work`**：
`AsyncLogger` 的 sink 列表是共享的，复用 `work` 会把指标混进业务日志文件——
业务日志按事件写、闲时是空的，指标按固定节拍写，混在一起既不好 grep 也没法画曲线。
独立 logger 意味着独立队列 + 独立线程 + 独立文件（`sysmon` vs `work`），
指标写慢了不会拖累业务日志，反之亦然。

**关键实现点**：

| 点 | 做法 | 原因 |
|---|---|---|
| 文件命名 | `FileSink(dir, keepDays, "sys_", /*plain=*/true)` | 前缀同时决定 `cleanupOldLogs` 的删除范围，`log_*` 与 `sys_*` 互不越界 |
| 行格式 | `plain=true` → 只写 `[时间] 内容` | 带上 `[T:线程号]` 会干扰 grep 和画图 |
| 首次建文件 | `init()` 里写一行 `# sysmon: ...` 字段说明 | 现场拿到文件不用翻文档；文件已存在且非空时不重复写 |
| CPU 使用率 | 必须先取基线再求差 | 单次读 `/proc/stat` 只能得到开机以来的平均值，没有参考价值 |
| 退出响应 | 分片睡眠 200ms，不是 `sleep(5000)` | 否则每次重启要卡满一个采样周期 |
| 关闭开关 | `sysmon.enabled=false` → 不建线程、不建文件 | 监控是辅助功能，关掉对业务零影响 |

**一个踩过的坑**：不能写成

```cpp
kv("temp", readCpuTemp(t), f1(t) + "C");   // ✗ C++ 实参求值顺序未定义
```

`f1(t)` 可能先于 `readCpuTemp(t)` 求值，拿到旧值 `0.0`。第一版就是这样把 `uptime`
写成了 `0s`（`/proc/uptime` 实际是 49.46）。必须先把结果读进局部变量再拼字符串。

**代价**：8000 秒/天 × 5s = 1.7 万行/天，约 3~4MB/天，按 `box.logKeepDays`（默认 7 天）
清理，最多占 25MB 左右。相对"跑三天卡死查不出原因"，这个代价可以接受。

### 8.2 FX 串口协议（`src/data_layer/fx_plc/fx_plc_instance.cpp`，618 行，**别随手改**）

- 串口参数来自 `plcSerial`：默认 9600 / **7 数据位** / 偶校验 / 1 停止位。
- 帧格式：`STX(0x02) + 命令码 + 地址 4 字符 + 数量 2 字符 + ETX(0x03) + 校验和 2 字符`。
  校验和 = STX 之后到 ETX（含）逐字节相加，取低 2 位十六进制。
- 读地址换算（`readM` 为例）：`wordAddr = 0x0100 + (m/16)*2`，`bitOffset = m%16`。
- 写地址换算：X → `0x0400 + linear(x)`，Y → `0x0500 + linear(y)`，M → `0x0800 + m`；
  其中 `linear(x) = (x/10)*8 + (x%10)`（把八进制写法转成线性位号）。
- 响应：`0x06`=ACK，`0x15`=NAK，`0x02...0x03`=带数据。

⚠️ **已知的三处协议隐患**，见 §13.6。

## 9. 点位表（数据驱动的核心）

**这是本项目的关键设计**：哪些点要采、哪些点算故障、命令写哪个地址，全在数据里，不在代码里（详见 `include/common/config/config_object.h`）。

### 9.1 三个核心结构

```cpp
struct SignalConfig {          // 一个有语义的 PLC 点
    std::string name;          // 内部名："washing" / "fault"
    std::string point;         // 软元件："Y74" / "D28"
    SignalReport report;       // REPORT_PROPERTY(进变化上报) / REPORT_EVENT(进故障上报) / REPORT_NONE(只本地用)
    std::string cloudKey;      // 上报字段名；空 = 用 point 大写（"Y74"）
    std::string comment;
    int normalValue = 0;       // 正常值。X50 是低电平有效，所以 =1
};

struct ServiceConfig {         // 一个可被云端调用的动作
    std::string name;          // "start" / "reset"

    std::map<std::string,std::string> write;  // 选择条件 → 软元件
    std::string comment;

struct AcquisitionConfig {     // 采集清单，按软元件类型分组

};
```

## 12. MQTT 协议

> 详细设计与取舍见 **`docs/MQTT通信框架-设计与实现.md`**；本节只列口径。

### 12.1 硬约束（云端 Flexem 平台要求，**不能改**）

1. `retain = false`
2. `QoS = 0`
3. `cleanSession = true`（每次重连都要重订阅，见 `MqttClient::handleConnect`）

clientId **直接用 boxNo**——云端靠它区分设备，两台同号会互踢。

### 12.2 topic 与载荷

topic 前缀：`flexem{sep}{boxNo}{sep}{endpoint}`，`sep` 由 `mqtt.topicSeparator` 决定，
**默认 `.`（生产抓包格式）**；改成 `"/"` 即为 Excel 配置写法。

| 方向 | topic | 载荷 |
|---|---|---|
| 订阅 | `flexem.{boxNo}.command` + `flexem/{boxNo}/command` | 命令 JSON（见下） |
| 订阅 | `flexem.{boxNo}.read` + `flexem/{boxNo}/read` | `{"D142":null,"M1":null,"boxNo":"123456","time":null}` |
| 订阅 | `flexem.{boxNo}.reboot` + `flexem/{boxNo}/reboot` | `{"reboot":1,"boxNo":"123456","time":...}` |
| 发布 | `flexem.{boxNo}.commandreply` | `{"message":"success","time":1780000000}`（time 为整型） |
| 发布 | `flexem.{boxNo}.monitor` | 海天 `{"D142":5,"boxNo":...,"time":...}`；驿公里带 `sState/stepName/deviceStatus` |
| 发布 | `flexem.{boxNo}.pushalarm` | 故障点位 + `faultName` + `boxNo`/`time` |
| 发布 | `flexem.{boxNo}.readdata` | 请求的点位值平铺 + `boxNo`/`time` |

**订阅恒为点号 + 斜杠两份**（6 条），发布只用 `topicSeparator` 一种：
两种都发会让云端收到重复上报；只订一种则云端换写法就要改盒子。

下行命令用 **JSON 字段名**区分（解析在 `CommandParser::classifyCommand`）：

```jsonc
{"Manual start":1, "boxNo":"123456", "mode":"1"}   // 启动，mode 仅驿公里必填(1/2/3)
{"stop":1, ...}            // 海天停止
{"reset":1, ...}           // 复位
{"washcar stop":1, ...}    // 驿公里停止
{"machine abort":1, ...}   // 驿公里中止 M206
{"reset safely":1, ...}    // 驿公里安全复位 M203
{"stop work":1, ...}       // 驿公里停止营业 M501
{"stop service":1, ...}    // 驿公里停止营业2 M510
{"reboot":1, ...}          // 默认只记录，不执行退出
```

`plcId` 不再是必需字段：payload 不带时由 `BusinessLayer::makeOperation` 按机型兜底
（驿公里 = `plcTcp.plcId`，海天 = `fx_plc_01`）。

## 13. 已知缺口与技术债 ★ 改代码前必读

这些不是 bug 报告，是**当前实现的真实状态**。要动相关逻辑，先看这里。

### 13.1 三个定时上报任务的驱动 —— 【已完成】

`executeValueChangeTask` / `executeFaultReportTask` / `executeDailyReportTask`
原来在整个项目里只有定义、没有调用点（精简版删 `LobbyService` 时连带删掉了定时器）。

**现状**：`ReportScheduler`（`include/business_layer/report/report_scheduler.h`）
由 `BusinessLayer::start()` 启动，一个线程按 `timing.*` 驱动这三个方法。
它**不认识 MQTT、也不检查链路**——只把报文推进 `upBuffer`。
"断链怎么办"由 `UplinkPump`（不消费）+ `UplinkBuffer`（同类只留最新）负责。

### 13.2 `read` / `reboot` 没订阅 + `handleRead` 只读不发 —— 【已完成】

**现状**：
1. `MqttClient::start` 生成 6 条订阅（3 endpoint × 点号/斜杠），
   `handleConnect` 逐条 subscribe，`handleMessage` 用 `topicToEndpoint_` 查表放行。
2. `CommandParser::extractRequestedPoints` 收集点位 → `BusinessLayer::handleRead`
   调 `IWashCarService::readPoints` → 推 `READDATA`（平铺 + `boxNo` + 整型 `time`）。
3. `CommandType::REBOOT` 分支只记 WARN。

### 13.3 `point on/off/reset/status`、`clearAlarm`、`changeMode` 在 MQTT 侧的入口

`CommandType` 枚举里**都定义好了**，`BusinessLayer::dispatch` 也**都实现了转发**，
但 `CommandParser::classifyCommand` **目前不产生这些类型**——因为协议文档里没约定它们的
JSON 字段名（正式版走的是 HTTP 8080）。

所以：能力齐了，缺的只是一行"字段名 → 枚举"的映射。要开会话时在
`command_parser.cpp` 的 `classifyCommand` 里加判断即可，业务侧零改动。

其中 `changeMode` 还有硬约束：`reqSource != "http"` 直接返回 false
（`washcar_service_base.cpp`），所以**维修模式在精简版里无法通过 MQTT 切换**。

### 13.4 没有持久化补发

`UplinkBuffer` 是内存队列，进程退出即丢。断链期间的行为见 §7.4：
`monitor/readdata` 只留最新快照、重连补一条，**历史过程无法还原**；
`commandreply` 最多攒 128 条，超过丢最旧。
正式版有 SQLite outbox 落库补发，精简版刻意去掉。

### 13.5 命令在下行泵线程里同步执行 —— 【已解决】

老实现里 `CommandRouter::onMessage` 在 mosquitto 接收线程里跑，驿公里启动命令包含
`sleep(200ms)` + `waitForConfirm`（最长 3s），会占住 MQTT 线程 3.2 秒。

**现状**：MQTT 回调只把 `RawMessage` 塞进 `rawBuffer` 就返回（微秒级），解析与执行在两条独立线程上；
命令在 `DownlinkPump` 自己的线程里执行，阻塞的是泵，不是网络线程。
代价：**命令串行执行**（一条命令执行完才处理下一条）——对洗车机这种单机设备是正确的语义。

### 13.6 FX 协议的三处隐患（`fx_plc_instance.cpp`）

| 位置 | 问题 | 影响 |
|---|---|---|
| `readS` | `int addr = s/8; int bitOffset = addr % 8;` —— bitOffset 取的是 `(s/8)%8`，应为 `s%8` | **只有 S0~S7 正确**。海天只用 S0 所以没事；**驿公里点表用了 S0~S81，非 0 步号可能读错位**。若真机上驿公里状态判定异常，先查这里 |
| `forceY` | `addrLowStr/addrHighStr` 声明后**从未 sprintf** 就塞进帧 | 发出去的是未初始化栈内容。当前点位表只写 M/X，**没有调用者**，属于潜伏 bug |
| `forceX/forceM` | 帧长 9 字节，缺 FX 协议规范的 1 字节数据域 | 真机可能回 NAK。现场若"写 M 点偶发失败"，查这里 |

> 这三条是从代码读出来的推断，**没有真机验证过**。改之前先抓串口报文确认。

### 13.7 采集周期 —— 【已支持配置】

`DeviceService` 构造时读 `machine().acquisition.intervalMs`：`>0` 用之，否则 **500**；
低于 **100** 夹到 100（串口来不及回包，只会把失败日志刷满）。
采集循环用 `steady_clock` 扣掉本轮的 IO 耗时再补 sleep，周期不漂移。

**踩过的坑**：`machine` 段校验不过时整段**静默回退内置表**（只打一行日志，不拦启动），
里面写的 `intervalMs` 一起失效。现在启动横幅会明确标出来源：

```
- 采集周期 700ms (来自 config.json 的 machine 段), 点位 29 项, 服务 4 项
- 采集周期 1000ms (来自内置默认表), 点位 29 项, 服务 4 项     ← 你写的没生效
```

判断依据是 `ConfigManager::machineFromConfig()`。看到"内置默认表"就去查
`[Config] machine.*` 那几行日志，里面写了回退原因。

### 13.8 MQTT 层的注意点

| # | 点 | 说明 / 影响 |
|---|---|---|
| 1 | 双格式订阅可能重复执行 | 云端若**同时**往 `flexem.123456.command` 与 `flexem/123456/command` 发同一条命令，盒子会执行两次。当前云端只发一种；出现时按 `time` 做 3s 窗口去重（加在 `CommandParser` 里最合适） |
| 2 | `readdata` 会省略采不到的点 | 不用 0 冒充。若云端要求"全量键"，需改为填 `null` 并同步协议 |
| 3 | `topicSeparator` 配错的表现 | 下行仍能收（订阅双份），**上行全静默**。排查上报问题时先看配置和 `[MQTT] 已连接, 发布前缀` 日志 |
| 4 | 日报依赖"整分命中" | `executeDailyReportTask` 内部按 `hh==H && mm==M` 判断；`ReportScheduler` 的日报检查间隔被夹到 `[1000, 5000]`ms，并用 `lastDailyReportDate_` 限一天一次，因此不会漏 |
| 5 | **broker 启动时不可达 → 进程退出** | `MqttClient::start()` 在 `mosquitto_connect_async` 同步失败时返回 false → `PresentationLayer::start()` 返回 false → `main` `return -1`。盒子上电早于网络就绪就会反复起不来。属**改造前既有行为**，本次未动；建议做有限次重试（见 §14 待办） |
| 6 | 上行泵断链时的 200ms 空转 | 每 200ms 检查一次 `isConnected()`，占用可忽略。但**断链时队列不消费**，所以 `pushalarm` 会攒着等重连，云端可能收到"迟到的报警" |

### 13.9 其他

- **无单元测试**（正式版有 4 个，精简版没带）。
- `stateMachine.logStateTransition` **仍是死配置**：状态机切换日志恒开，没有代码读这个开关。
  要么在状态机里补判断，要么从配置模板里删掉。
  （`mqtt.reconnectBaseSec` / `reconnectMaxRetry` 已接上，见 §8 配置表）
- `m_currentStatus` 是共享成员，多个并发命令会互相覆盖（当前下行泵单线程调用，安全）。
- 海天 `getWashCarStatus` 里有一大段 `std::cout` 打印整张 PLC 状态表，
  复位时每次都会刷屏，生产环境建议降级为 `LOG_DEBUG`。
- `trace_context.h` 里的 `[TEMP_DIAG]` 日志是临时诊断用，量很大，可清。
- `common/topics.h` 现在只有 `presentation/mqtt_client.cpp` 在用（3 个订阅 endpoint 的宏），
  里面遗留的一批 HTTP topic 宏（`WASHCAR_HTTP_*`）已经没有任何引用，可以清掉。

### 13.10 业务层现场读 PLC —— 【已解决】

`DeviceService::viewAllDeviceStatus()` 早先有一句兜底：

```cpp
if (!gateway_.hasSnapshot()) {
    gateway_.poll();          // ← 已删除
}
```

后果见 §7.5：业务线程和采集线程抢同一条串口、PLC 断线时每条命令都去开一次串口、
状态判定拿到的"此刻值"与按快照设计的判定逻辑混用。

**现状**：删掉兜底，改为纯读 `cache_`；同时在 `DeviceService::start()` 里先同步采一轮，
保证 `start()` 返回时缓存已就绪。已用 mock PLC 计数验证：缓存就绪后连续 100 次读，
PLC 读调用次数零增长；断线场景连续 50 次读全部返回空表，同样零增长。

**遗留（性能，非正确性）**：采集线程每轮 `poll()` 是同步阻塞的，`DeviceService::readOne`
对每个点位单独发一次请求。驿公里点位表共 113 个点（D 12 + M 19 + S 82），
一轮可能超过 1 秒的采集周期，导致 monitor 状态滞后。
根治要给 `IPlcInstance` 加批量读接口：`S0~S81` 地址连续，一次 FC1 读 82 个线圈即可；
D 寄存器按地址块用 FC3 合批；M 点按段合并。目标把一轮请求压到 5 次以内。

## 16. 术语表

| 术语 | 含义 |
|---|---|
| **软元件** | 三菱 PLC 的存储单元：D=数据寄存器(16位)、M=内部继电器(位)、X=输入(位)、Y=输出(位)、S=状态继电器(位) |
| **组读** | X/Y 一次读 1 字节 = 8 个位，组号 = 地址/10，位号 = 地址%10 |
| **点表 / 点位表** | `MachinePointTable`，一台机器的软元件清单 + 语义映射 |
| **S 步号** | 驿公里用 STL 步序表示流程位置；S20~S81 = 洗车中，S81 = 完成，S5 = 待机 |
| **D142 / D1000** | 海天用 D142 表示洗车步骤 0~10；驿公里用 D1000 存故障码 |
| **reqSource** | 命令来源标记：`mqtt` / `http`。维修模式只接受 `http` |
| **enforce / log_only** | 状态机守卫的两档，见 §10.3 |
