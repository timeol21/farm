## MQTT broker 日志可读化 + 历史查询边界
- 结论：mosquitto 不存消息历史（QoS0 无订阅即丢、无 retain、cleanSession=1）；`mosquitto.db` 只存 retained/离线队列。
- mosquitto 1.6.9 **没有** `log_timestamp_format`（2.0 才加），日志时间戳只能是 epoch 秒，只能在读日志侧转换。1.6.9 有 `log_type all/subscribe/unsubscribe`、`connection_messages`、`autosave_interval`。

## journalctl 只看到"一点点"的原因（手册新增 21.8）
- 主因：`journalctl -f` 是跟随模式，历史只回显最后 10 行；看历史要去掉 `-f`，或 `-n 300 -f`。
- 次因：mosquitto 默认 `log_type` 不含 subscribe，稳定连接期间**零日志**（不记每条消息、永不记 payload）；手动前台 `sudo mosquitto -v` 的输出不进 journald；journald `Storage=auto` 无 `/var/log/journal/` 时重启即丢；conf.d 缺 `log_dest stdout` 时 journald 只剩 systemd 启停行。
- 自查四连：`wc -l` 数行数 / grep Starting-Stopped 看重启边界 / `--since today` + grep connected / `--since ... --until ...` 对齐联调时间段。
- 已在 `docs/盒子上部署Broker与MQTTX联调手册.md` 追加 21.8（21.7 之后）。

## Timer::scheduleRepeated 分析
- 定位：`Timer` 是"业务层通用周期任务调度器"，一条线程 + 一个 vector<ScheduledTask>，`runLoop` 每 500ms 轮询一次，到期就同步执行；不是 Qt/asio 定时器，也区别于 `DeviceService::startTimer`（自己一条采集线程）和 `DetectionService` 内部线程。
- 首次 scheduleRepeated 用 `m_runningUpload.compare_exchange_strong` 抢线程启动权；后续调用只 push_back。
- 首跑立即执行（`lastExecuteTime==0` → 置 now 并 run），之后按 `nowMs-lastExecuteTime>=intervalMs`。
- 注册点：`lobby_service.cpp:55-57` + `:60`（LobbyService 构造函数），四个任务：
  dailyReport=`timing.dailyReportCheckIntervalMs`(默认60000)、valueChange=3000、fault=3000、AI=`ai.workingIntervalMs`(2000)。
- 业务落点：`onDailyReportTimer:1030`/`onValueChangeTimer:1050`/`onFaultTimer:1070`/`updateAIDetectionFrequency:1414`。
- 坑：①实际粒度 500ms（`sleep_for(500)`），interval<500 等于 500；②单线程串行，慢任务拖累其他；③三个 stopXxxMonitor 共用同一个 `stopUpload()`（停一个停全部）；④stopUpload 不清 m_tasks、不重置 lastExecuteTime → 重启后旧任务会立刻重复跑 + 重复 push 造成叠加；⑤`isRunningUpload()` 因构造期已起线程恒为 true，`startDeviceStatusUpload:902` 的守卫永远返回 SERVER_TOO_MANY_Repeat（该方法当前无调用者）；⑥`TimingProcessing`/`m_running`/`g_device_interval` 是死代码。
- 启动竞态：LobbyService 构造(299) 早于 mqtt immitDependence(303+)，前 1~2 拍回调打到空 mqtt → `[CommandService] CMD_REPORT_DROP ... service_null`（null 已判，不崩）。

## MachinePointTable 的来源与结构（device_acquisition_task.h:26）
- 链路：config.json `machine.<boxType>` → `from_json` 填 `DeviceConfigRoot::machines`(config_serialization.h:324) → `ConfigManager::parseJson` 选出 `activeMachine_`(config_manager.cpp:241-269) → `machine()` 返回 `const&`(config_manager.h:31) → `main_test.cpp:187 cfg.machine()` → `DeviceAcquisitionTask` 存引用(device_acquisition_task.cpp:20)。
- 三级回退：JSON 优先 → 无 `machine.<boxType>` 用 `default_point::getPointTable` 内置表 → machineType 不一致/validatePointTable 失败也回退内置表（均打 `[Config] machine...` 启动日志）。
- 内置表：`src/common/config/default_point.cpp:6` haiTian(fxSerial)、`:109` yiGongLi(modbusTcp)，`static const` + lambda，进程内单例。
- 结构：`MachinePointTable{ machineType, protocol, description, acquisition{intervalMs,dPoints,yPoints,mPoints,xPoints,sPoints}, signals[SignalConfig], services[ServiceConfig{write:map<条件,软元件>}], homeSensors, dailyReportSignals, faultSignals, resetSignals, faultCodes, keyStatePoints }`；`SignalConfig{name,point,report(SignalReport 枚举),cloudKey,comment,normalValue}`。
- 引用安全：指向单例成员 `activeMachine_`（值存储、地址固定），reload 重新赋值不会悬垂；`protocol` 决定 getTasks 选 Fx/Tcp 实现；`acquisition` 只被采集层用，`signals/services` 给业务层，`faultCodes` 只做日志翻译。
- 校验规则 validatePointTable(config_manager.cpp:49)：点位格式 D/Y/M/X/S+数字、signal.name 唯一、signal.point 必须在采集清单内、五个引用列表的名字必须存在。

## default_point 内置表 + fallback 机制
- `haiTianPointTable()`(default_point.cpp:6) / `yiGongLiPointTable()`(:109) 在**匿名 namespace** 里（内部链接，外部只能经 `getPointTable` 进）；内部是 `static const MachinePointTable table = []{...}();` —— 立即执行 lambda：用多语句+for 循环构造后 `return table;` 初始化外层 static，**不是回调、不注册**，那对 `()` 是当场调用。
- `static` = 首次调用时构造一次（C++11 magic static 线程安全）；`const` + 返回 `const&` = 之后不可改、不拷贝、全进程共享一份。
- `getPointTable(boxType)`(default_point.cpp:183) 只是 `boxType=="yiGongLi" ? yiGongLiPointTable() : haiTianPointTable()` 的三元分派。
- `const MachinePointTable fallback = default_point::getPointTable(root_.box.boxType);`(config_manager.cpp:242) 在 `ConfigManager::parseJson()` 里，跟 `activeMachine_` 的三路赋值(:251/:259/:263)是一组：既当内置表自检对象(:244)，又当三处回退的赋值源。是**值拷贝**，可改 `const auto&` 省一次深拷贝。
- 触发链：`main_test.cpp:82 ConfigManager::instance().load()` → `load()`:124 先 `applyDefaults()`(:119 也走 getPointTable) → `:165 parseJson()` → `:242`。
- **模板里不写 machine 段**（default_config.cpp:62 注释 + root to_json 不含 machines），所以现场 config.json 通常没有 machine 段 → 一定用内置表；想覆盖只能手写 `"machine": {...}` 进 JSON（from_json 支持）。`default_config::get()` 的 machines 为空，所以 applyDefaults 里的 `it != end` 分支永不成立。

## IPlcInstance 多态（FxPlcInstanceSet::plcMap_）
- `plcMap_` 是 `unordered_map<string, unique_ptr<IPlcInstance>>`，但**堆上实际对象是派生类**：`main_test.cpp:140` 插 `TcpPlcInstance`（驿公里）、`:153` 插 `FxPlcInstance`（海天）；`addPlc(unique_ptr<IPlcInstance>)` 只做指针隐式转换 + move，**没有对象切片**（按值传基类才会切）。
- `plc->connect()` 是虚函数动态绑定：对象头 vptr → 派生类 vtable → `connect` 槽位（iplc_instance.h:10 纯虚；fx_plc_instance.h:12 `override`）。静态类型只决定"第几个槽"，实际地址运行时取。
- 必要条件三条都满足：纯虚 `=0`、派生 `override`、基类 `virtual ~IPlcInstance()=default`（:8）——后者对 `unique_ptr<IPlcInstance>` 必须，否则 delete 基类指针是 UB。
- `FxPlcInstance::connect()` 幂等（`fx_plc_instance.cpp:96 if(connected_) return true`），所以 `getFxPlcStatusList/acquisitionFxPlcData` 每轮调 connect 不会重复 open 串口。

## ConfigManager::machine() 是重载，不是默认参数
- 两个函数：无参 `machine()` **inline 在头文件** `config_manager.h:31` → `return activeMachine_;`；带参 `machine(const std::string& boxType)` 定义在 `config_manager.cpp:211` → `root_.machines.find(boxType)`，没配回退 `default_point::getPointTable`。
- `boxType` **无默认参数**，所以 `cfg.machine()` 零实参只能命中无参版（编译期重载决议）。运行期只是取成员引用：无函数调用、无 map 查找、无 fallback、无拷贝。
- 调用者：无参 → main_test:187 / mqtt_command.cpp:69 / washcar_service_base.cpp:247 / washcar_state_machine_test:63；带参 → washcar_state_machine.cpp:31（状态机按自己机型取）、yi_gong_li_command_test:1479。
- 两者返回值**可能不是同一对象**：带参版返回 `root_.machines` 里的那份（或 default_point 的 static），无参版返回 `activeMachine_`（parseJson 时 `activeMachine_ = it->second` 的**拷贝**）。内容相同、地址不同，别用 `&a == &b` 判断。
- 别给带参版加 `= ""` 默认值，会与无参版二义性编译失败。

## DeviceStatus() : type_(0) {} 的真相
- 位置 `include/data_layer/device/device_status.h:19`；另一个 protected 3 参构造 `(deviceId, type, name)`(:9) 给派生类用。
- 默认构造存在的三个理由：① `DoorLock::getStatus()`(door_lock.cpp:43) 直接 `make_unique<DeviceStatus>()`，而 DeviceStatus 非抽象（无纯虚）所以能直接实例化；② `FxPlcStatus()=default`(fx_plc_status.h:9)、`CameraStatus()=default`(camera_status.h:11) 都依赖基类默认可访问；③ `FxPlcStatus` 是 `DeviceData` 成员(device_data.h:43)，`DeviceData()=default` 又要默认构造它。
